## 1 引言

### 1.1 编写目的

本文档依据《本科毕业设计任务书》（2026-09-01 下发）及《需求规格说明书》，给出共享快递袋系统（英文名 **Shared Express Mailer System**，缩写 SEMS，开发阶段的工程目录与代码制品统一使用该名称）的总体架构、功能模块、核心业务流程、数据库概要结构、接口规范、关键技术方案与安全设计，作为后续编码实现、数据库详细设计、测试与部署的依据。

本文档的预期读者：指导教师、毕业生本人、答辩评审专家，以及后续参与系统实现与维护的开发人员。

### 1.2 项目背景

随着电子商务与快递业务规模持续增长，一次性快递包装消耗量大、回收率低。国务院《固体废物综合治理行动计划》（国发〔2025〕14 号）明确提出加快推进快递包装绿色转型。共享快递袋以循环复用方式替代一次性包装，但目前投放、取用、回收、消毒、复用等环节普遍依赖线下人工登记，存在**库存信息不透明、流转过程不可追溯、站点间调度依赖经验、损坏与遗失责任难以认定**四类突出问题。

本系统面向校园、社区、写字楼等快递集散场景，以共享快递袋为循环载体，通过信息化手段实现快递袋**分配、使用、回收、消毒、调度**的全流程在线管理，形成"取—用—还—洗—调"闭环，并结合网络空间安全专业方向落实认证、鉴权、审计等安全机制。

## 2 总体设计

### 2.1 设计目标

1. 实现快递袋"取—用—还—洗—调"全流程线上化，全程状态可追溯（每步流转写日志、留操作人）。
2. 高并发取袋场景下库存**不超发、不漏发**（Redis 原子扣减 + 同步补偿 + 对账兜底）。
3. 三类角色权限边界清晰，接口无越权，操作全程可审计。
4. 前端响应式适配 PC 与移动端，扫码取袋 / 还袋在手机端即可完成。

### 2.2 设计原则

| 原则                           | 落地方式                                                                                                                                             |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 前后端分离                     | 前端 Vue 3 独立工程，后端只提供 RESTful API，交互为纯 JSON                                                                                           |
| 无状态服务                     | 服务端不保存会话，身份凭 JWT 携带，便于水平扩展                                                                                                      |
| 状态集中管控                   | 快递袋状态只允许经统一状态机组件流转，业务代码不得直接 UPDATE 状态字段；3.2 转移表是状态流转的**唯一权威**，正文其他章节与本表冲突时以本表为准 |
| 实物为锚                       | 可用库存与实物一致：袋离开"空闲"即不可领用，库存回补只发生在实物回归（扫码确认）时点                                                                 |
| 缓存优先                       | 库存读扣减走 Redis，MySQL 为权威底账，定时对账纠偏                                                                                                   |
| 安全内建（Security by Design） | 认证、鉴权、参数校验、审计以框架层切面/拦截器统一实现，不依赖各业务代码自觉                                                                          |
| 统一出口                       | 全局异常处理器 + 统一 JSON 响应体，前端只需处理一种响应结构                                                                                          |

```
└──────────────┬───────────────────────┬──────────────────┘
┌──────────────▼──────────┐ ┌──────────▼─────────────────┐
│ 数据层  MySQL 8.0        │ │ 缓存层  Redis 7            │
│   业务底账 · 流转日志     │ │   库存原子扣减(Lua)         │
│   审计日志               │ │   JWT 黑名单 · 预扣凭据(TTL)│
│   (权威数据源)           │ │   开单计数 · 限流 · 验证码   │
└─────────────────────────┘ └────────────────────────────┘
```

**架构决策说明：**

- **采用单体分层而非微服务**：系统业务规模为校园级（站点数 ≤ 数十、袋量 ≤ 万级、峰值并发申领为瞬时低频），微服务带来的注册中心、网关、链路追踪等复杂度远超收益；按模块分包保持清晰的逻辑边界，未来可平滑拆分。
- **Nginx 同时承担静态托管与反向代理**，前端构建产物与 API 同域，规避跨域复杂度（开发期由 Vite proxy 代理）。
- **WebSocket 推送服务内嵌于应用层**，不引入独立消息中间件；推送内容为轻量状态变更通知，单机 WebSocket 会话管理即可满足规模。

### 2.7 关键设计决策记录

| 决策                   | 结论                                                                                | 主要理由与备选方案                                                                                                           |
| ---------------------- | ----------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 库存扣减位置           | Redis Lua 原子扣减为主，MySQL 行级条件更新兜底                                      | 备选"仅 MySQL 行锁/乐观锁"在并发取袋时热点行竞争明显；Redis + TTL 过期机制是任务书明确要求                                   |
| 架构形态               | 单体分层                                                                            | 备选微服务复杂度不匹配毕设规模（见 2.3）                                                                                     |
| 认证方案               | JWT（含 token_version）+ Redis 黑名单                                               | 纯 JWT 无法主动失效（登出/封禁/调岗即失效需求）；jti 黑名单解决单设备登出，用户级 token_version 解决封禁/重置/调岗的全量吊销 |
| RBAC 形态              | 三角色简化 RBAC（用户-角色两表 + 注解权限点），管理角色继承普通用户能力             | 角色固定且少，完整五表模型收益低；保留 user_role 关联表结构便于扩展                                                          |
| 站点管理员与站点的绑定 | `sys_user.station_id` 单站绑定（一岗一站）                                        | 满足"站点管理员限本站"的全部场景且实现最简；若未来需一人多站，升级为 user_station 多对多并让数据权限走 IN 集合，接口不变     |
| 袋的站点归属语义       | `bag.station_id` = **当前存放站点**，随回收确认、调拨入库等实物转移事件变更 | 备选"归属永不变化"将导致跨站归还账实分离（详见 3.2 表后说明）                                                                |
| 消息推送               | 原生 WebSocket + JSON 消息                                                          | 备选 STOMP/SockJS 协议较重；推送主题少且固定，原生更可控                                                                     |
| 订单与袋状态关系       | 袋状态为权威事实，订单状态跟随联动（联动表见 3.6）                                  | 避免双状态各自演化产生不一致；订单超时等由定时任务驱动                                                                       |
| 报废控制               | 站点管理员直接登记报废（留痕）+ 平台事后审计                                        | 备选"申请-审批流"需增设待复核状态与审批单据，超出毕设规模必要复杂度；报废本身已受状态机约束且全程留痕，审计可事后稽核        |

## 3 核心领域设计：快递袋全生命周期状态机

### 3.1 状态定义

正常循环采用四态，业务活动“还、洗、调”通过订单、消毒批次和调拨单独立留档；另保留四个扩展态。

```text
图 3-1 快递袋生命周期
空闲 --扫码申领--> 已分配 --提交寄件--> 使用中 --站点回收确认--> 待消毒
 ↑                    │                                      │
 └--未使用回收--------┘                  消毒合格自动入库------┘
标记归还：袋保持使用中，订单转待回收确认。
维修完成：维修中 → 待消毒；无法修复/达到复用上限 → 报废。
调拨：空闲 → 调拨在途 → 空闲；遗失：已分配/使用中/调拨在途 → 已遗失 → 待消毒。
```

| 状态码       | 状态名   | 含义                                                 | 计入站点可用库存 |
| ------------ | -------- | ---------------------------------------------------- | ---------------- |
| IDLE         | 空闲     | 已上架，可被申领                                     | 是               |
| ALLOCATED    | 已分配   | 用户扫码申领成功，尚未提交寄件信息                   | 否（已预扣）     |
| IN_USE       | 使用中   | 已寄件，处于寄送/使用环节                            | 否               |
| TO_DISINFECT | 待消毒   | 回收确认完成，进入待消毒区                           | 否               |

**站点归属（`bag.station_id`）变更规则**：`bag.station_id` 语义为**当前存放站点**。变更仅发生在实物转移时点——#4/#5/#7/#8 回收确认改为确认站点、#17 调拨入库改为目标站点、#20 找回改为找回登记站点、#21 修正时按需同步；登记站点在建袋/批量生成时指定（见 5.4），空闲期间即写入 `station_id`。#6 标记归还只在订单上记录 `return_station_id`，不改变袋归属。所有"限本站"校验按事件上下文比对操作人站点与该事件涉及的目标站点（见 4.4），而非无差别套用 `station_id=?` 过滤。

**#21 修正的库存口径**：#21 的库存规则以"库存归属站点（`bag.station_id`）是否变更"为准，**不受源/目标状态是否相同影响**——跨站修正一律同步 `station_id` 并向两站推送；库存增减按 #21 公式（可为 0）。同站同态作为无操作请求拒绝（4102）；跨站同态仍需转移归属并执行库存/推送规则。

**非法跳变控制**：状态机组件仅注册上表 21 条合法转移；任何未注册的 (当前状态, 事件) 组合一律拒绝并抛出业务异常（**袋状态机拒绝一律 4102**；订单/单据状态不允许属非状态机管辖的另一类，统一 4105，边界见 6.4），拒绝记录写入审计日志。转移执行采用"DB 条件 UPDATE（`WHERE status=前态 AND version=?`）"作为并发最后防线，防止两笔操作同时通过前置校验（如两人同时申领同一只袋）。

**#4 与 #5 的取用规则**：站点扫码后由系统按**绑定订单状态自动路由**，无需人工判断——订单已取消/不存在 → #4（袋回空闲）；订单仍为待寄件 → #5（进待消毒并关闭订单）；站点扫码时可勾选「曾寄出」标注（用户迟寄未登记）——命中时按待消毒路径处理并计 `use_count`（迟寄补救，见 9.1 风险登记）。**平台管理员代操作**：表中"站点管理员（本站）"均含平台管理员全站代操作（前置校验不变、日志标记代操作），5.x 接口表中的"本站站点管理员"同理。**批量接口**（回收确认、上架入库、出库、消毒登记，语义见 6.2）逐只执行转移并返回逐袋结果明细，单只失败不影响其余。

**责任认定口径**：使用中遗失超时 → 责任主体为申领用户；调拨在途遗失 → 责任主体为源站（由平台管理员裁决）；已分配留置超期 → 责任主体为申领用户。责任与处置结论在确认遗失时由平台管理员填写（`liability_record.responsible_user_id` 可空=责任待定，结论记于 `conclusion/decided_by/decided_at`，见 8.2）。

**订单级操作说明**：用户"撤回申领"与定时任务的"24h 超时取消"是**订单级操作**，只把订单置为已取消并删除预扣凭据，不改变袋状态、**不释放在持袋数额度**（袋保持已分配，等待站点管理员执行 #4 未使用回收或 #5 回收确认；袋离开已分配/使用中两态时才计数 −1）。订单状态定义见 3.6。

### 3.3 状态机实现设计

```text
BagStateMachine（唯一流转入口）
  fire(bagCode, event, operatorContext, clientRequestId)
    1. 幂等检查：以 clientRequestId + bagCode 查重（Redis SETNX，命中直接返回首次结果；
       批量接口逐袋独立幂等，接口入口的请求级幂等见 9.6）
    2. 查询袋当前状态（带乐观锁读取）
    3. 在转移注册表中查找 (currentState, event) → 转移规则
       未找到 → 抛 BizException(4102, "状态非法流转") + 记审计
    4. 执行前置校验（规则携带的 guard）：
       a. DB 校验：订单状态、归属、调拨明细、use_count 等
       b. Redis 原子校验（申领类）：在持袋数计数、取袋日频次、库存扣减与预扣凭据写入
          在同一个 Lua 脚本内一次完成（见 7.2），任一不满足则整体不落账
    5. 事务内：
       a. 条件 UPDATE bag SET status=目标, station_id=?, version=version+1
          WHERE code=? AND status=前态 AND version=?
          影响行数=0 → 并发冲突，终止（重复领取最后防线，报 4103）
       b. INSERT bag_transfer_log(...)
       c. 规则附带的业务动作（订单联动、Redis 库存增减、记录表写入等）
    6. 事务提交后：推送 WebSocket（库存/订单主题）
    7. 阶段一（申领）失败：Lua 失败分支（返回 0/-1/-2/-3/-4）无库存/计数变更，直接返回错误或按需重试；
       Lua 成功而 DB 事务未落地时按 R0 同步补偿（见 7.2 失败分支矩阵）
```

事件与状态以 Java 枚举定义（`BagStatus`、`BagEvent`），转移注册表为静态 `Map<BagStatus, Map<BagEvent, TransitionRule>>`，新增流转只需注册规则，不改主流程。

**调拨建单与袋状态流转的互斥协议**：两类操作都先按袋码升序取得 `bag` 行的 `SELECT ... FOR UPDATE` 锁，再在同一事务中校验并写入。调拨建单在锁定所有目标袋后逐只检查袋码存在、状态为空闲、当前 `station_id` 等于调拨源站，并检查活动调拨引用，再插入待出库单和明细；状态机持有袋行锁后，用当前读复核待出库/在途调拨引用，再执行状态条件更新。这样调拨建单与申领、维修、直接报废、状态修正按袋行锁串行，避免“校验无锁后另一事务建单”的竞态；批量锁按袋码升序降低死锁风险。事务提交或回滚时释放锁。具体字段与索引见《数据库设计说明书》4.2.6、4.2.17。

#### 3.4.2 归还—消毒—复用流程（"还"与"洗"）


#### 3.4.3 调拨流程（"调"）

```text
看板显示站点 A 库存低于预警阈值、站点 B 富余
  → 平台管理员创建调拨单(B→A, 数量N)，逐只扫码锁定明细袋（建单即锁定：
     取袋前置校验"袋未被未出库调拨单引用"）
  → B 站（源站）管理员执行调拨出库：袋 空闲→调拨在途，B 站库存 −N
  → 抵达后 A 站（目标站）管理员扫码核收入库：袋 调拨在途→空闲（归属改 A 站），
     A 站库存 +N，调拨单闭环
  → 出库后 48h 未核收 → 平台管理员确认在途遗失（袋→已遗失，调拨单异常，记责任）
异常处理：仅"待出库"状态的调拨单可整单取消，明细袋解锁回空闲；出库扫码失败
（实物缺失/码损）→ 将该袋从调拨单剔除（**剔除仅对仍空闲的袋生效**，状态回空闲）后其余继续出库；
袋已非空闲（如被转维修/报废/状态修正）时无法剔除，须由平台管理员终止调拨单（走既有终止路径，未出库明细解锁回空闲）后另行处置。
单据状态机：待出库 --首只出库--> 在途（未出库明细仍可继续出库或由平台剔除解锁）
→ 全部核收 --完成--> 已完成；部分核收/在途遗失确认后单据置"异常"并保留差异记录，
由平台管理员决定继续核收或终止（终止时未出库明细解锁回空闲）。
```

#### 3.4.4 库存盘点流程

站点管理员发起盘点 → 选择本站点 → 系统展示各状态账面数 → 录入各状态实际数 → 保存生成盘点单（差异自动计算）。账实一致时盘点单自动闭环并记录闭环时间；有差异时系统按状态数量差异生成袋级候选清单，盘点单保持待修正。候选清单不能确定具体实物差异，须由平台管理员现场核验后再按转移表 #21 修正状态并填写原因；状态修正不要求也不自动关联盘点单号，修正后盘点单也不会自动闭环。待修正单仅可作废重盘。修正涉及跨站归属时，同步 `station_id` 并向两站推送，库存增减按 #21 公式（可为 0）。

### 3.6 订单状态设计

订单状态枚举 `OrderStatus`（订单表带 `version` 乐观锁与 `client_request_id` 幂等字段）：

| 订单状态        | 含义       | 对应袋状态                | 进入条件（事件）                                 |
| --------------- | ---------- | ------------------------- | ------------------------------------------------ |
| PENDING_SEND    | 待寄件     | 已分配                    | 扫码申领成功（转移#2）                           |
| IN_USE          | 使用中     | 使用中                    | 提交寄件（#3）                                   |
| PENDING_CONFIRM | 待回收确认 | 使用中（订单已标记归还） | 标记归还（#6）                                   |
| FINISHED        | 已完成     | （袋已进待消毒）          | 回收确认（#7/#8）                                |
| CANCELLED       | 已取消     | （袋保持已分配，待#4/#5） | 用户撤回 / 24h 超时取消 / 未使用袋回收确认（#5） |
| LOST            | 已遗失     | 已遗失                    | 平台管理员遗失确认（#18；已取消订单转已遗失=终态覆盖） |

- **"超时"不是订单状态**，是标记字段（`timeout_flag` + `timeout_time`）：寄件后 7 天未归还置位并推送提醒，状态仍为 IN_USE，直至归还或遗失确认。
- **在持袋数计数与袋状态同步**：申领建单（袋→已分配）时计数 +1；**撤回/超时取消（订单→已取消）不 −1**（袋仍在用户手上）；仅当袋经 #4/#5/#7/#8/#18/#21 离开 {已分配, 使用中} 两态时才 −1，与状态变更在同一事务/同一调用链内完成（见 7.2）。
- 订单状态与袋状态严格按上表联动，联动由状态机转移的伴随动作完成，不允许单独改订单状态。
- 并发保护：订单表 `version` 乐观锁 + 条件更新；`express_company + tracking_no` 联合唯一，防重复运单。

## 4 角色与权限设计（RBAC）

### 4.1 角色定义

| 角色       | 角色码         | 说明                                                                         |
| ---------- | -------------- | ---------------------------------------------------------------------------- |
| 普通用户   | USER           | 校园/社区/写字楼内取袋寄件、归还、查询本人订单的自然人                       |
| 站点管理员 | STATION_ADMIN  | 负责某一座站点运营的账号，通过`sys_user.station_id` 与站点绑定（一岗一站） |
| 平台管理员 | PLATFORM_ADMIN | 全局用户/站点/快递袋/订单管理、调拨调度、数据统计、审计查询、异常裁决        |

### 4.2 权限模型

采用简化 RBAC：`sys_user`（含 `status`、`station_id`、`token_version`）— `sys_user_role`（用户-角色关联）— `sys_role`（三行固定数据）。接口级权限点以后端注解 `@RequireRole("STATION_ADMIN")` 声明，由统一拦截器校验，不引入可配置权限表（角色固定，避免过度设计；如需扩展可平滑升级为"角色-菜单-权限点"五表模型）。

**账号与角色开通路径（初始管理员来源）**：初始化 SQL 预置**平台管理员账号**（手机号 `13800000000`，昵称"平台管理员"，初始口令 `Sems@2026`，`must_change_password=1`）；首次登录及被重置密码后**强制改密**——登录/重置密码响应携带 `mustChangePassword`，未改密前拦截器对该账号仅放行"修改密码、退出登录、续签"三个接口（见 5.1）；之后由平台管理员在用户管理中**创建账号并授予角色**（`POST /users`），站点管理员创建时**必须绑定站点**（`PUT /users/{id}/station`），站点管理员的 `stationId` 由此写入并随 JWT 携带——这是 JWT 中 `stationId` 声明的唯一来源。调岗/换绑站点/角色变更时自增该用户 `token_version`，旧 token 立即失效（见 7.1）。

JWT 载荷携带 `uid、role、stationId（站点管理员专属）、tokenVersion、jti、exp`，拦截器一次解析即可完成认证与粗粒度鉴权。

### 4.3 角色—功能权限矩阵

**继承规则：站点管理员与平台管理员天然具备普通用户的全部业务能力**（取袋、寄件、标记归还、查询本人订单），且同样受"在持袋数 ≤3"与取袋频次约束。矩阵与 5.x 接口表的权限列冲突时，以接口表为准。平台管理员对站点类操作可**全站代操作**（前置校验不变、日志标记代操作）；5.x 权限列中"本站站点管理员"均含平台管理员代操作，"本人"为数据范围限定（非角色），"登录用户"含管理角色继承（见上）。

| 平台管理员不受站点限制                                                       | 角色判断放行；代操作行为在日志中标记                                                                                                                                                                                                                                                                                                                                                                             |

所有"按 id/编码查详情 / 修改"类接口在 Service 层执行**资源归属二次校验**（查到记录后比对归属字段），拦截器漏判时仍有兜底。

## 6 接口设计规范

### 6.1 RESTful 约定

- 路径前缀 `/api/v1`，资源名用复数名词（`/bags`、`/orders`、`/stations`、`/users`），子资源用嵌套（`/stations/{id}/stock`）。
- 资源根登记：订单资源根统一为 `/orders`（用户侧与管理侧同根，按权限列与数据范围区分）；**`/borrows` 为登记的唯一例外**——取袋动作族（申领、提交寄件、撤回）以动作语义独立成根，便于 Nginx 对其单独限流（见 11.2）；全站不设 `/admin` 前缀。
- 动词语义：GET 查询、POST 创建/触发动作、PATCH 部分更新、PUT 全量替换（角色授予、站点绑定等"整体替换"语义）、DELETE 删除/取消。动作型业务（如"回收确认""遗失确认"）采用 `POST /资源/动作` 形式。
- 查询参数：分页 `pageNum`（默认 1）、`pageSize`（默认 10，最大 100）、排序 `orderBy=field,asc|desc`（字段白名单）；时间区间 `beginTime/endTime`。
- 写操作幂等头：`clientRequestId`（客户端生成的 UUID），见 9.6；适用清单与豁免项：登录后全部写接口启用，匿名写接口（注册/登录/验证码）不启用接口级幂等（由验证码与锁定另行防护），确需防重放的匿名写接口键退化为 `api+clientRequestId`（无 uid）。

### 6.2 统一响应格式

```json
{ "code": 0, "message": "success", "data": { } }
```

- `code=0` 表示成功；非 0 为错误码（见 6.4）。分页数据放在 `data.records / data.total / data.pages`。
- **例外**：`batch-generate` 的二维码 ZIP 下载为二进制流响应（`Content-Disposition` 附件下载），是统一 JSON 之外唯一声明的例外。
- **批量接口的部分失败**：逐袋执行的批量接口（回收确认、上架入库、出库、消毒登记、**调拨出库、调拨核收、在途遗失确认**）在 `data` 中返回逐袋结果明细（成功/失败 + 错误码），单只失败不影响其余；**批量上限默认 ≤500 只/批**（未单独标注处），**消毒登记 ≤200 为特例**；声明为"整批原子"的接口（batch-generate）单独标注；批量数量超限统一由 3001 承载。
  **逐袋结果明细的统一信封（定，全站唯一形态）**：`data = { total, success, failed, items: [...] }`——`total`/`success`/`failed` 为整数计数，`items` 为逐袋明细数组。
  `items` 的元素字段名固定为 `bagCode`、`success`、`code`、`message` 四个，**任一字段都必须在每条元素上出现**（成功项 `code` 取 0，不得留空——响应体开了 `non_null` 过滤，留 null 会让字段整个消失，字段集合时有时无则接口测试与前端都无法写死断言）。
  补充字段仅两处、且不改变上述形态：回收确认在信封上追加 `proxy`/`crossStation`/`directWithoutMark`（对应 7.6 的三档审计 action，供前端即时告知操作人被记成了哪一种）；消毒登记在信封上追加 `batchNo`/`result`（批次号与批次汇总）。
  **配套约定**：批量上限 500 时 `items` 可能被截断，故计数字段以服务端返回的值为准，客户端不要用 `items.length` 反推。
  **批量动作的入参形态**：逐袋执行类动作用 `bags: [{ bagCode, ... }]`（元素可带该袋专属参数，如回收确认的 `shippedBefore`、消毒的 `result`、出库的 `remark`）；仅"创建单据时提交一份袋码清单"的 `POST /allocations` 用 `bagCodes: [字符串]`，因为建单只是登记清单、没有逐袋参数。两者语义不同，不要混用。
- 所有异常由全局异常处理器转换为统一格式（处理链见 6.6）：参数校验失败（400）、未认证（401）、无权限（403）、业务异常（**HTTP 按 6.6 映射表** + 业务错误码）、系统异常（500，不向前端暴露堆栈）。

### 6.3 认证约定

除 `/auth/register`、`/auth/login`、`/auth/captcha` 与健康端点 `/api/health`（仅返回存活状态，不泄露内部信息）外，所有接口要求请求头 `Authorization: Bearer <JWT>`；`401` 前端清除本地 token 并跳转登录；`403` 提示无权限。

| 4110   | 袋已被调拨单锁定                  | 申领/转维修/报废/状态修正命中"袋被未出库调拨单引用"                                |

| 5102   | 库存计数未就绪（可重试）          | 站点计数初始化中（Lua 首查 `stock:init` 命中即返回）                                                                |
| 5103   | 库存对账中，请重试                | 对账互斥标记持有期内（Lua 返回 -2，指数退避重试耗尽后）                                                                |
| 5000   | 系统内部错误                      | 兜底                                                                            |

## 7 关键技术方案设计

### 7.1 JWT 认证设计

- 载荷：`sub=uid`、`role`、`stationId`（站点管理员专属，来源见 4.2）、`tokenVersion`、`jti`（唯一 ID）、`iat`、`exp`；**解析侧固定 HS256**（拒绝其他 alg），密钥为 ≥32 字节 CSPRNG 随机串，从环境变量注入，不入库不入码，支持双密钥轮换窗口（旧密钥只验不签，过渡 24h）。
- 有效期：access token 2 小时；前端剩余 <30 分钟时调 `POST /auth/refresh` 静默续签（旧 jti 入黑名单）。**空闲会话的续签触发方式**：前端以定时器（每分钟）检查剩余时长并触发续签，页面停留、无操作亦如此；存在活跃 WebSocket 的页面同理——续签后旧 jti 失效，旧连接会在下次心跳（≤30s）被断开，**前端重连前先刷新 token 并重建 WS**（约定见 7.3）。
- **两级主动失效**：
  1. **单设备登出**：登出/续签时将 `jti` 写入 Redis 黑名单（key `auth:deny:{jti}`，TTL=token 剩余有效期）；
  2. **用户级全量吊销**：`sys_user.token_version`（禁用、重置密码、改密、调岗/换绑站点/改角色时自增），自增后同步 `DEL auth:userver:{uid}` 使缓存立即失效；拦截器比对 token 载荷中的版本与该值（Redis 仅作 60s 读加速；降级期直读 DB 比对，见 7.2）不一致即拒绝。被禁用账号的存量 token 在**下一次请求即被拒绝**，"封号即失效"由此兑现；WebSocket 通道在下次心跳（≤30s）断开。
- 拦截链：`OncePerRequestFilter` 解析 token → `HandlerInterceptor` 做 `@RequireRole` 鉴权 → Service 层数据权限校验（见 4.4）。
- 多端登录策略：允许多端同时在线（每端独立 jti）；登出仅失效当前端，全量失效靠 token_version。

### 7.2 Redis 库存并发扣减方案（防超发/漏发）

**语义约定**：可用库存 = 站点 IDLE 袋数，DB 为权威、Redis 为读写视图；库存回补只发生在实物回归（扫码确认）时点（见 2.2 "实物为锚"）。业务取消时限统一为 24h（见 3.5），预扣凭据 TTL 25h 仅作凭据。

**数据结构**

| Key                               | 类型         | TTL            | 说明                                                                                                      |
| --------------------------------- | ------------ | -------------- | --------------------------------------------------------------------------------------------------------- |
| `stock:available:{stationId}`   | String(int)  | 无（对账维护） | 站点可用库存计数                                                                                          |
| `stock:hold:{orderNo}`          | String(json) | 25h            | 预扣凭据（orderNo/stationId/bagCode），**不承担取消语义**；供 R0/R1/R2 删除，并作 R0 补偿幂等凭据与 R3 启动期孤儿检查读取 |
| `stock:init:{stationId}`        | String(标记) | 300s           | 计数初始化互斥标记（SETNX，防惊群；Lua 首查，命中即返回 5102）                                                                       |
| `stock:reconcile:{stationId}`   | String(标记) | 120s           | 对账互斥标记（Lua 命中返回 -2→5103，客户端指数退避重试）                                                                  |
| `stock:sentinel:{stationId}`    | String(标记) | 无             | 站点计数哨兵键（随计数初始化写入；启动与巡检校验，缺失即触发重建——覆盖 Redis 被清空但连接正常的情形） |
| `borrow:open:{uid}`             | String(int)  | 14 天滑动（每次申领重置）      | 在持袋数计数（≤3，原子校验；袋处于已分配/使用中 +1、离开这两态 −1；撤回/超时取消不释放；对账重建时 SETEX 显式续期）                                                |
| `borrow:daily:{uid}:{yyyyMMdd}` | String(int)  | 当日+1天       | 取袋日频次计数（≤10）                                                                                    |

**Lua 原子扣减脚本**（申领时执行，"检查-扣减-记录"三步原子化，防超发）：

```lua
-- KEYS[1]=stock:available:{sid}  KEYS[2]=stock:hold:{orderNo}  KEYS[3]=stock:init:{sid}
-- KEYS[4]=stock:reconcile:{sid}  KEYS[5]=borrow:open:{uid}     KEYS[6]=borrow:daily:{uid}:{yyyyMMdd}
-- ARGV[1]=预扣凭据JSON  ARGV[2]=凭据TTL秒  ARGV[3]=open上限  ARGV[4]=daily上限  ARGV[5]=daily TTL秒
if redis.call('EXISTS', KEYS[3]) == 1 then return -1 end   -- 计数初始化中 → 5102
if redis.call('EXISTS', KEYS[4]) == 1 then return -2 end   -- 对账中 → 5103，客户端指数退避重试
local avail = tonumber(redis.call('GET', KEYS[1]) or '-1')
if avail == -1 then return -1 end                          -- 计数未初始化 → 5102
if tonumber(redis.call('GET', KEYS[5]) or '0') >= tonumber(ARGV[3]) then return -3 end  -- 在持袋数超限 → 4104
if tonumber(redis.call('GET', KEYS[6]) or '0') >= tonumber(ARGV[4]) then return -4 end  -- 取袋频次超限 → 4109
if avail < 1 then return 0 end                             -- 库存不足 → 4101
-- 以下四步在同一脚本内原子完成；前面任一检查未通过则整体不落账
redis.call('DECR', KEYS[1])                                -- 库存扣减
redis.call('SETEX', KEYS[2], ARGV[2], ARGV[1])             -- 预扣凭据
redis.call('INCR', KEYS[5])                                -- 在持袋数计数
redis.call('INCR', KEYS[6])                                -- 取袋日频次
redis.call('EXPIRE', KEYS[6], ARGV[5])
redis.call('EXPIRE', KEYS[5], 1209600)                     -- 计数 TTL 14 天滑动续期（对账重建时 SETEX 显式续期）
return 1
```

**两阶段流程与五条回补路径（R0–R4）**

```text
阶段一 预扣:  单个 Lua 原子完成「在持袋数计数<3 + 取袋日频次<10 + 库存 DECR + 写预扣凭据」
              → DB事务(建订单PENDING_SEND + 袋条件UPDATE→已分配 + 流转日志)
              ├─ 成功 → 返回订单号
              └─ 失败(含同袋竞争4103/宕机前检测到的任何异常) → R0（先回查幂等，见下）
阶段二 确认:  提交寄件 → DB事务(订单→使用中 + 袋→使用中) → DEL 预扣凭据

Lua 返回值与失败分支矩阵（实现时逐条对应）：
  1=成功；0=库存不足(4101)；-1=计数初始化中/未初始化(5102，可重试)；
  -2=对账中(5103，指数退避 0.5/1/2/4s 重试、累计 ≥5s，耗尽返回 5103)；-3=在持袋数超限(4104)；-4=取袋频次超限(4109)
  · Lua 返回 0/-1/-2/-3/-4 → 库存未扣减、计数未自增，**不回补库存**，仅按需重试
  · Lua 成功但 DB 事务失败 → R0：先按 client_request_id/order_no 回查（已提交则按成功幂等回放、不再补偿），确认未提交才执行补偿 Lua：INCR 库存 + DEL 预扣凭据 + 在持袋数计数 −1
    （日频次不退还，符合 3.5"含已撤回/已取消"口径）
  · Lua 成功后进程崩溃（无同步补偿机会）→ 计数漂移由 R4（≤30 分钟）与每日开单计数对账纠正

R0 同步补偿（主路径，必需分支）: 阶段一 DB 事务失败时，在同一请求内先按
    client_request_id/order_no 回查订单与袋状态——已提交则按成功幂等回放（不再补偿），
    确认未提交才执行补偿：单个 Lua 原子完成「存在 stock:hold:{orderNo} 才 DEL 凭据 +
    INCR 库存 + 在持袋数计数 −1」（以凭据存在性作幂等凭据，防止重复补偿）；
    stock_compensation_log 降为审计用途；补偿失败则记 ERROR 告警，
    交由 R4 与每日开单计数对账兜底。
R1 用户撤回:  订单置已取消（**不释放在持袋数额度**：袋仍在用户手上，计数不变），
    DEL 预扣凭据；**不回补库存**，袋保持已分配，等待站点 #4 未使用回收/#5 回收确认
    闭环时才计数 −1（#4 扫码时库存 +1）。
R2 24h 超时取消（定时任务扫 DB，而非扫 Redis）: 订单 PENDING_SEND 且
    created_at 超过 24h → 置已取消，同 R1（计数不 −1）；袋由站点 #4/#5 收回闭环时释放额度。
R3 崩溃窗口兜底: 进程在 Lua 扣减后、DB 事务前宕机 → 无订单行、预扣凭据成孤儿。
    应用启动时扫描 stock:hold:* 与 DB 订单比对（启动期一次性，量小）：
    孤儿凭据 DEL 并记告警；兜底主体为 R4 与每日开单计数对账——库存按 DB（IDLE 袋数）、
    在持袋数计数按 DB（袋处于已分配/使用中两态的当前持有订单数）纠偏。
R4 定时对账（每30分钟）: 逐站点 SETNX stock:reconcile:{sid}（TTL 120s）
    → 间隔 1s 连续两次读 DB COUNT(IDLE)，两次一致才继续（降低与在途请求相撞）
    → SET 写回 Redis（不设 TTL）→ DEL 标记。
    对账期间扣减请求命中标记返回 -2（→5103），客户端指数退避重试（0.5/1/2/4s，
    累计 ≥5s），耗尽后返回 5103 由用户稍后再试；
    差异写入告警日志并计入 /alerts「对账差异」类（见 5.6）。残余竞态（已过 Lua、
    尚未提交 DB 的在途扣减）最迟被下一轮对账收敛，且"同一只袋不被两人领取"由
    DB 条件 UPDATE 独立保证。
```

**DB 兜底**：袋表条件 UPDATE（`WHERE code=? AND status='IDLE' AND version=?`）是重复领取的最后防线；Redis 故障时的**降级路径**见下。

**计数初始化与故障恢复**：应用启动及 Redis 故障恢复时，逐站点 `SETNX stock:init:{sid}` 作为互斥标记（写入时点=重建开始前，删除时点=重建完成、计数写回之后；只有成功取得该标记的重建任务才可删除旧 `stock:available:{sid}` 并按数据库 `COUNT(IDLE)` 重写，避免未获得互斥权的并发任务误删持有者计数，`COUNT=0` 也写入 0 值）；初始化完成前该站点的申领请求由 Lua 首查标记命中返回 5102（可重试）。**降级触发**：连续 3 次 Redis 命令异常（10s 窗口）→ 熔断打开，申领直走 DB 行级路径（按袋码锁定行并条件 UPDATE，并发正确性由行锁保证，仅损失吞吐）。**恢复判定**：连续 3 次 PING 成功方视为 Redis 恢复，随后走初始化流程重建计数并关闭熔断；**哨兵键校验**：站点计数哨兵键 `stock:sentinel:{sid}` 随初始化写入且不设 TTL，启动与巡检时缺失即按"未初始化"触发重建（覆盖 Redis 被清空但连接正常的情形）。降级期间不写 Redis 计数，避免恢复后计数偏高。初始化由启动/恢复事件单线程触发，初始化失败由 R4 兜底并告警。

**降级期各项 Redis 依赖控制的行为**（不得静默放行）：

| 控制项                           | Redis 故障/熔断期行为                                                                        |
| -------------------------------- | -------------------------------------------------------------------------------------------- |
| 库存扣减                         | 走 DB 行级路径（按袋码条件 UPDATE），正确性由行锁保证                                        |
| 在持袋数 ≤3 / 取袋日频次 ≤10 | 退化为 DB 计数校验（COUNT 袋处于已分配/使用中两态的当前持有订单数 / COUNT 当日订单数，走`(user_id,status)` 与时间索引）；**校验与建单并入同一事务**：`SELECT ... FOR UPDATE` 锁定该用户在持订单行 + 条件 INSERT，限额不被并发击穿 |
| 幂等（clientRequestId）          | 由`bag_order.client_request_id` 与 `stock_compensation_log` 唯一键兜底                   |
| jti 黑名单（单设备登出）         | 降级期 **fail-open**：账号级失效由下行 token_version 行直读 DB 保证、保持即时；设备级登出失效窗口 ≤ access token 剩余有效期（≤2h）；降级期请求记 WARN 审计，恢复后黑名单继续生效 |
| token_version（禁用/重置/调岗）  | 不受影响：降级期直读 DB 比对，保持即时失效（权威在 DB，Redis 仅 60s 读缓存）                                                   |
| 登录失败锁定 / 应用层限流        | 退化为 Nginx 按 IP 限流兜底（`login_zone` 10r/m burst 5、`borrow_zone` 30r/m burst 10、`scan_zone` 120r/m burst 30，超限 429，见 11.2），恢复后重置计数                                                      |
| 恢复动作                         | 重建`stock:available`、`borrow:open`、`borrow:daily` 与 `stock:sentinel` 后关闭熔断                        |

**防重复领取**：Redis 扣减解决"库存数量"并发；"同一只袋不被两人拿走"由 DB 条件 UPDATE 保证，两道防线独立生效。

**并发目标**：单站点 500 并发申领压测下，成功数 = min(请求数, 库存数)，无超发、无漏发（验证方法见 12.2）。

### 7.3 WebSocket 实时推送设计

- 端点：`/ws`。**认证采用首帧鉴权**（避免 token 进 URL 与 Nginx 访问日志）：连接建立后 10 秒内发送 `{"type":"auth","token":"<JWT>"}`，服务端校验通过方可订阅；超时或校验失败即断开。
- 订阅授权（服务端按 JWT 声明生成订阅白名单，越权订阅直接拒绝并审计）：

| 主题                     | 允许订阅方               | 推送时机                                                                         |
| ------------------------ | ------------------------ | -------------------------------------------------------------------------------- |
| `station/{id}/stock`   | 该站点管理员、平台管理员 | 可用库存增减（申领 −1；建档入库/未使用回收/消毒合格入库/调拨入库 +1；空闲转维修 −1；直接报废（前态=空闲）−1；状态修正按源/目标站判定增减（源/目标态为触发条件之一）、跨站推送两站（见 3.2 #21）；调拨出库 −1） |
| `station/{id}/recycle` | 该站点管理员、平台管理员 | 用户标记归还（提醒确认）                                                         |
| `user/{uid}/order`     | 仅 uid 本人              | 订单状态变更、超时提醒                                                           |
| `platform/dashboard`   | 仅平台管理员             | 全局库存/订单异动、预警触发                                                      |

- 消息格式：`{"topic":"...","type":"...","data":{...},"ts":...}`。
- **连接期失效复查**：心跳（ping/pong，30s）时复用 HTTP 侧校验逻辑（jti 黑名单 + token_version + 账号状态 + **exp 过期**），任一失效即主动断开——禁用/调岗用户的推送通道同步失效；续签会拉黑旧 jti、此类断连属预期，前端**重连前先刷新 token 并重建 WS**（见 7.1）。
- 会话管理：`ConcurrentHashMap<主题, Set<Session>>`；推送在业务事务提交后触发（`TransactionSynchronization.afterCommit`），避免"事务回滚但消息已发"。
- 前端：断线指数退避重连（1s/2s/4s/…上限 30s），**重连前先刷新 token**；`visibilitychange` 回前台立即重连并**重新拉取当前页数据**兜底（不上消息 ACK/重放机制）。

### 7.4 快递袋编码与二维码方案

- **编码规则**：`SJB-{规格码1位}-{出厂年月yyMM}-{5位流水}-{1位校验码}`，示例 `SJB-L-2609-00001-4`（共 18 字符）。流水段按「规格码 + 出厂年月」分组、从 `00001` 起连续分配；**编码不承载站点语义**（原"站点归属预留段"取消），归属一律以 `bag.station_id` 为准。
- **校验码算法（本文档即权威定义，实现唯一出处为 `com.sems.common.util.BagCodeUtils`）**：取字符表 `ALPHABET = "0123456789ABCDEFGHIJKLMNOPQRSTUV"`（32 个字符，下标即取值）；把袋码去掉 4 个连字符与末位校验码得到码体（示例的码体为 `SJBL260900001`）；对码体第 i 个字符（i 自 1 起）取字符值 `charValue`（数字 `0`–`9` 映射 0–9，字母 `A`–`Z` 映射 10–35），计算 `sum = Σ (i × charValue(cᵢ))`，校验位 = `ALPHABET[sum mod 31]`（结果落在 `0`–`9` 与 `A`–`U`，满足袋码正则 `[0-9A-Z]`）。**为什么模 31 而不是模 10**：模数取质数且接近字符表容量，单字符误输被检出的概率约为 30/31，远高于模 10 的模数冲突概率；同时校验位本身扩大了码空间，抬高按码枚举的成本（见 9.1「二维码伪造/克隆」对策）。校验位不参与任何签名，防伪边界见下文。
- **二维码内容**：`https://{域名配置}/m/bag/{bagCode}`（域名由配置项 `sems.qrcode.domain` 注入（键清单见 11.2），变更域名后旧二维码需换标重印，或在旧域名保留 301 跳转；域名不参与编码与签名），微信"扫一扫"可直接打开袋详情/申领页；系统内扫码先调 `GET /bags/{bagCode}/info` 校验袋码存在性与状态合法性（报废/遗失返回 4107 并提示）。
- **信息最小化（防枚举）**：`info` 接口对与操作人无归属关系的袋仅返回"规格 + 是否可领用 + 所在站点名称"；同一用户 1 分钟内 ≥10 次袋码查询失败 → 触发 5101 限流并记审计（风控线索；限流窗口口径见 3.5）。
- **生成**：后端 ZXing 批量生成 PNG（含编码文本下方标注），打包 ZIP 供平台管理员下载打印；新袋实物与标签核对后建档即为空闲，自动进入可申领库存。
- **识别**：移动端 H5 使用浏览器 `BarcodeDetector` API，不支持的浏览器降级引入 jsQR；站点管理员可使用 USB 扫码枪（等价键盘输入袋码），移动端提供袋码手输入口兜底。
- **防伪边界**：二维码为明文 URL、不做密码学签名——仿制标签**无法绕过**服务端状态机、归属校验与唯一约束，其危害限于"引导用户打开错误落地页"；异常扫码频次与地点作为审计线索（见 9.1 威胁条目）——**"地点"以 `bag_transfer_log.station_id` 为唯一数据来源**（不新增字段），如需展示扫码地点，复用流转日志的操作站点。**真标换贴**（把 A 袋标签贴到 B 袋）服务端无法检测，属已认领的残余风险，依靠回收/上架外观与数量核验、盘点差异、流转地点与时间异常审计发现（见 3.4.4）。

### 7.5 定时任务设计

统一约定：调度使用独立线程池（4 线程）；每任务声明幂等键、执行超时（5 分钟）、失败告警；扫描类任务分批（LIMIT 500）+ 命中索引，禁止全表扫描。

| ---------------------- | ---------- | ----------------------------- | -------------------------------------------------------------------------------------------------------------- |

### 7.6 操作日志与审计

- 注解 `@AuditLog(module="快递袋管理", action="消毒登记")` 标注在 Controller 方法上，AOP 环绕采集：操作人、角色、IP、UA、模块/动作、入参（**密码等敏感字段脱敏后**再记录）、结果（成功/失败+错误码）、耗时。登录失败、越权拦截（2001/2002）、状态机拒绝（4102）、报废与状态修正、**回收确认（按上下文写不同 action：直投/跨站/未标记直投，可按动作筛出）**等关键事件**必须**入审计。**登录/操作 IP 的可见与展示**：仅平台管理员在审计查询中可见，列表默认部分掩码（如 `192.168.*.*`），详情可看完整值（查看行为记审计）。
- 异步落库（独立线程池 + 有界队列）与**队列饱和策略**：队列满时——关键事件降级为同步写；普通事件写入本地应急文件（启动时回放入库）并累加丢弃计数器（落库 `sys_metric`，经 `/stats/dashboard` 的 `auditDropCount` 与 `/alerts`「审计队列丢弃」展示告警、另写 ERROR 日志），确保审计写入高峰（往往正是攻击高峰）不拖垮业务、也不静默丢失。
- 防篡改三层：①应用层不提供审计表的修改/删除接口；②**数据库账号对 `audit_log / login_log / stock_compensation_log` 仅授予 INSERT、SELECT**；③保留期 ≥180 天，备份加密存储（见 11.3）；审计数据的归档清理由**独立运维账号**按 7.5 执行（导出 → GPG 加密 → 校验后删除），**应用账号 INSERT/SELECT 授权不变**。
- 审计查询仅平台管理员可见（见 5.6）。

> **业务单号生成规则（定，实现唯一出处为 `com.sems.common.util.BizNoUtils`）**：结构为 `前缀 + yyyyMMddHHmmss + 6 位数字段`，总长 22，适配各单号列的 `varchar(32)`。前缀登记：`BO` 快递订单（`bag_order.order_no`）、`AL` 调拨单（`allocation_order.allocation_no`）、`IC` 盘点单（`inventory_check.check_no`）、`DB` 消毒批次（`disinfect_record.batch_no`）。
> **6 位数字段为什么不取纯随机数**：单号列均有唯一索引，撞号会直接让业务事务失败；纯随机段在同一秒内服从生日悖论分布——同秒生成 1000 次即有约 39% 概率至少撞一对，批量出库与并发申领完全够得着。故取 `(启动时随机偏移 + 进程内自增计数) mod 10^6`：模运算下自增序列是单射，**同一秒内前 100 万个单号两两不同**；偏移取自 `SecureRandom`，每个进程启动时不同，外部无法预判下一个单号。跨秒由时间戳段区分，跨实例由随机偏移区分，最终由唯一索引把关（见 9.6）。

敏感字段处理：`phone` 存明文（业务必需）；本人信息与普通业务出参脱敏为 `138****1234`，仅限平台管理员访问的用户管理列表返回完整登录手机号用于账号核对与维护；`password` 仅存 BCrypt 摘要；收件人手机号存 `recipient_phone_mask`（掩码，展示用）与 `recipient_phone_hash`（HMAC-SHA256 + 密钥版本，**仅作留存证据，本系统不提供哈希比对入口**），不存完整号码。

| `rate:{uid或ip}:{api}`                     | String(int)  | 1 min 窗口     | 固定窗口限流（登录/取袋/扫码查询，见 9.6；窗口口径见 3.5）                                                                                                      |
| `stats:today:{stationId}`                  | Hash         | 当日 24 时+4h  | 今日取/还实时计数（写入点：申领成功 INCR borrow、回收确认 INCR return，看板读取；跨日自然过期）；平台看板按站点求和读取，`stats:today:0` 为可选的全平台汇总键 |

> **TTL 与淘汰口径（定）**：计数与安全类键多带 TTL（`borrow:open`、`login:fail`、`rate:*`、`idempotent:*` 等），`volatile-lru` 在内存压力下会**静默逐出**它们；而少数无 TTL 的键又回收不了、内存照样打满，故弃用 `volatile-lru` 改用 `noeviction`。Redis 采用 `maxmemory 512mb` + **`maxmemory-policy noeviction`**——内存打满时写入直接失败并触发 7.2 的熔断降级（行为明确、可测），不做静默逐出。**内存估算**：按毕设规模（站点 ≤100、日活 ≤5000、单键 ≤1KB）估算键空间 <50MB，512MB 余量充足。

## 9 安全设计（网络空间安全方向重点）

### 9.1 威胁分析与对策总览

| 威胁                        | 对应风险                                   | 设计对策                                                                                                                                               |
| --------------------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 身份伪装（Spoofing）        | 弱口令、token 被盗用                       | BCrypt 强哈希、失败锁定、验证码、JWT 短有效期+两级吊销（jti 黑名单 + token_version）、HTTPS 传输                                                       |
| 篡改（Tampering）           | 越权改单、恶意参数                         | 服务端状态机校验、参数校验（JSR-380）、乐观锁、预编译防注入                                                                                            |
| 抵赖（Repudiation）         | 操作后不承认                               | 全量审计日志（IP/UA/参数/结果）应用层只插不改 + 数据库账号仅授 INSERT/SELECT，保留≥180 天                                                             |
| 信息泄露（Info Disclosure） | 越权查询他人订单、敏感数据外泄             | 水平越权校验、手机号脱敏、袋信息最小化返回（7.4）、最小化采集（不采集身份证）、错误信息不暴露堆栈                                                      |
| 拒绝服务（DoS）             | 登录/取袋/扫码接口被刷                     | Nginx+应用层双重限流（Nginx 三桶 10/30/120 r/m、超限 429；应用层超限 5101/4109，见 11.2/9.6）、验证码升级、有界队列异步审计                                                                                                     |
| 权限提升（Elevation）       | 普通用户调用管理接口                       | 三层防线：拦截器注解鉴权 → Service 归属校验 → 状态机终审                                                                                             |
| 二维码伪造/克隆             | 换标、仿制落地页                           | 仿制标签无法绕过服务端状态机、归属校验与唯一约束；编码含校验位提高枚举成本；袋信息最小化；异常扫码频次/地点审计追溯（地点数据来源=`bag_transfer_log.station_id`，见 7.4）                                    |
| 业务逻辑滥用                | 扫码刷袋、恶意占袋、撤回循环               | 在持袋数 ≤3（原子计数，撤回/超时取消不释放）、取袋 10 次/日、失败查询限流、撤回仅置订单取消不回补库存                                                                    |
| 内部人员舞弊                | 违规报废、修正状态、篡改盘点、异常回收确认 | 报废/状态修正/回收确认（含跨站与未标记直投）强制留痕并列入审计重点核查项；同类高频确认（阈值=同站点同操作人 10 分钟内确认类操作 ≥20 次，见 3.5）与流转异常触发看板告警；盘点差异单据支撑；审计表数据库层只插不改 |
| 风险接受（Redis 降级期）    | 单设备登出失效窗口 ≤2h                     | jti 黑名单降级期 fail-open（设备级登出窗口 ≤ access token 剩余有效期）；账号级失效由 token_version 直读 DB 保持即时；降级期请求记 WARN 审计（见 7.2） |
| 风险接受（迟寄场景）        | 袋确未回流且无运单记录时，用户可能被按留置/遗失追责 | 取消后宽限期内站点扫码可勾选「曾寄出」按待消毒处理（#4，计 use_count）；7 天留置升级前人工核验；残余风险（确实寄出但无任何记录）接受并记录于责任认定；不新增「取消后补登运单」接口（毕设规模取舍） |

### 9.2 认证与会话安全

- 密码策略：长度≥8 且含两类字符；BCrypt（cost 10）存储；传输仅经 HTTPS。
- 登录防护：同账号 5 次失败锁 15 分钟（`login:fail:{phone}`）；**锁定期满后首次登录须一次性图形验证码（TTL 3 分钟）**；登录成功/失败均写 `login_log`。
- 会话：access token 2h + 静默续签（7.1）；登出（jti 黑名单）、禁用/重置/调岗（token_version）**立即失效**；多端策略见 7.1。

### 9.3 访问控制（防越权）

- **垂直越权**：`@RequireRole` 注解 + 拦截器统一校验，管理接口在 Controller 层即拒绝普通用户。
- **水平越权**：三类强制校验——①订单类接口 `user_id` 一律取自 token，不接受前端传参；②站点管理员接口按**事件上下文站点**校验（见 4.4，含跨站归还的回收确认特例）；③按 id/编码取详情后再做一次归属比对（兜底）。
- **状态机终审**：即便权限与归属通过，非法状态转移仍被状态机拒绝（如站点管理员不能把一只"空闲"的袋确认为已回收——它根本不在回收流程中）。

### 9.4 注入与输入安全

- SQL 注入：MyBatis-Plus 全程预编译 `#{}`；代码规约禁止 `${}` 字符串拼接（排序字段等动态项用白名单映射）。
- 参数校验：Controller 入参 `@Validated` + JSR-380 注解（长度/格式/范围），袋码正则 `^SJB-[A-Z]-\d{4}-\d{5}-[0-9A-Z]$` 统一校验，防止任意字符串透传（前端校验规则见 10.4，后端为权威）。
- XSS：系统无富文本场景，响应头叠加 CSP（见 11.2）收窄注入面；会话不走 Cookie（JWT），降低会话劫持面。
- CSRF：无 Cookie 会话 + token 走 `Authorization` 头，天然免疫常规 CSRF；生产环境同域部署，CORS 默认关闭。

### 9.5 数据安全与脱敏

| 数据         | 存储                           | 展示                                |
| ------------ | ------------------------------ | ----------------------------------- |
| 登录密码     | BCrypt 摘要                    | 不可见                              |
| 手机号       | 明文（业务必需）               | 本人信息、普通业务出参与审计日志显示 `138****1234`；平台管理员用户管理列表显示完整登录手机号 |
| 收件人手机号 | 掩码 + HMAC-SHA256 哈希（含密钥版本，8.2） | 仅掩码展示；哈希仅作留存证据，不提供比对入口 |
| 运单号       | 明文                           | 本人与平台管理员可见；其余非归属人报 2002（管理端查看记审计） |

传输全程 TLS 1.2+（Nginx 终结）；数据库账号按最小权限授权（应用账号不授予 DROP/GRANT，审计表仅 INSERT/SELECT）；云服务器安全组仅放行 22/80/443（SSH 见 11.3 加固），MySQL/Redis 仅监听内网，Redis 设置 requirepass。

### 9.6 接口防护

- 限流：登录、取袋、扫码信息查询接口以 Redis 固定窗口限流（如 10 次/分钟/用户；窗口口径见 3.5），超限返回 5101；Nginx 侧三桶按 IP 并行兜底（见 11.2）。
- **幂等**：写操作统一携带 `clientRequestId`（客户端 UUID，服务端校验格式）请求头；服务端以 `idempotent:{uid}:{api}:{clientRequestId}` 为键去重（TTL 10min），命中已完成记录返回首次结果，命中"处理中"占位返回可重试提示。**幂等记录状态机与字段**：请求进入先 SETNX 写"处理中"占位（字段：status）→ SETNX 未明确返回 true（含 false 或空结果）表示未取得锁，按同一幂等键正在执行或被并发请求占用处理，返回可重试 5103，禁止并行执行业务；Redis 访问异常仍按降级矩阵放行。业务在数据库事务内成功后，缓存"已完成"结果仅在事务提交后写入 Redis；事务回滚时在 afterCompletion 清理处理中占位，非事务写操作立即写完成结果。任何业务失败由调用方删除占位，避免重试被自己的"处理中"挡住；记录清理仅依赖 TTL，无需定时任务。**适用与豁免**：登录后全部写接口启用；匿名写接口（注册/登录/验证码）不启用接口级幂等（由验证码与锁定另行防护），确需防重放的匿名写接口键退化为 `api+clientRequestId`（无 uid）。**幂等键粒度**：接口级幂等作用于请求入口；批量接口（回收确认、上架入库、出库、消毒登记）与状态机内部转移按 `clientRequestId + bagCode` **逐袋幂等**，避免第 2 只袋被误判为重复请求。重复申领另由"袋状态守卫 + DB 条件 UPDATE"兜底；取袋链路的库存扣减以 `clientRequestId` 为补偿幂等凭据（7.2 R0）。
- 上传：本系统无必需文件上传（二维码由系统生成），不开放用户上传功能。

### 9.7 供应链与依赖安全

Maven 侧接入 OWASP Dependency-Check、前端接入 `npm audit`，纳入构建流程；发现高危（CVSS ≥9）依赖时评估升级或替换并记录处置结论——作为网络空间安全方向的工程实践项。

- 扫码与归还用**全屏结果卡**反馈：成功绿、失败红，配文案与提示音；确认键高 48px 并二次确认。
- 订单与袋卡片：状态标签置顶 + 左侧 4px 语义色条，关键字段两行内，主操作右对齐。
- 站点端 PC：顶部常驻扫码输入框，表格行高 48px、行内操作不超过 2 个，回收与消毒走抽屉，提交后即时刷新行状态。
- 站点端手机：入库、消毒确认为全屏单任务页，按钮高 48px 大字，适配手持工位。
- 平台端 PC：240px 深色 `#1E293B` 侧边栏 + 白卡内容区；>1200px 常驻，768–1200px 收为 64px 图标条。
- 看板：KPI 四列卡（数字 28px），网格线 `#E2E8F0`，图例常驻并直接标注，列数 4→2→1 自适应；轴标 12px 次要色，tooltip 白底浮层，数字用 `tabular-nums` 对齐。
- 响应式：<768px 全站单列，**表格一律转为卡片列表（禁止横向滚动）**，看板列堆叠、侧边栏转底部导航。
- 移动端安全区：底部固定元素加 `env(safe-area-inset-bottom)`，容器高度用 `100dvh`；键盘弹起时底部操作栏隐藏或上推。

**袋码展示与流转时间线**（两项容易被忽略但直接在答辩中被看到）

- 袋码与二维码：袋详情卡二维码渲染尺寸 ≥160px、静区 ≥4 个模块，袋码用等宽字体展示并可一键复制，附打印视图（批量打印见 7.4）；扫码页含取景框、手输兜底入口与"已扫到"的即时反馈（见 10.3）。
- 流转时间线：袋与订单详情页用 Timeline 组件呈现全生命周期闭环——每个节点按本节状态色着色，当前态高亮，异常节点（报废/遗失/超时）标红并附原因，节点信息含**操作人、站点、时间与流转日志摘要**。这是"取—用—还—洗—调"闭环最直观的展示位，不得省略。

**空态、加载与异常态**（缺一即显廉价，逐页落实）

- 加载：列表/卡片/看板三档骨架屏，**占位尺寸与真实内容一致**，不得用整页 spinner 造成跳版。
- 空态：插画或图标 + 一句说明 + 主操作按钮（如"暂无待回收袋" + "去扫码"）。
- 错误态：网络失败给"重试"按钮（对应 5102），403/404 给专属页面而非空白。
- 状态双通道：绿色系标签必须带图标，全站状态标签在红绿色盲模拟下逐屏自查，红绿不得相邻。

**禁止事项（美观底线）**

1. 禁止在页面或组件内写死颜色十六进制，一切走 CSS 变量；
2. 禁止超过三种圆角，禁用大圆角、重阴影、渐变等消费级风格；
3. 禁止仅靠颜色区分状态，必须"色 + 文案"（必要时加图标）；
4. 禁止图表使用色板外的高饱和彩虹色，饼图不超过 3 类；
5. 禁止绕过变量直接使用 Element Plus 原生冷灰与默认亮阶；
6. 禁止以 info 灰作可点击色——可点击元素一律用主色蓝；
7. 禁止新增或调换语义色与快递袋状态的映射关系（本节即权威口径）；
8. 本项目**不做整站深色模式**（深色仅用于平台端侧边栏），全局声明 `color-scheme: light`，避免系统暗色偏好反色破坏已校验的对比度。

### 11.1 部署拓扑（云服务器）

```text
图 11-1 部署拓扑
Internet ──► 安全组(22/80/443)
   Nginx 443(TLS)
     ├── /          → /usr/share/nginx/html (Vue dist, SPA history 回退 index.html)
     ├── /api/      → proxy_pass http://127.0.0.1:8080  (Spring Boot)
     └── /ws        → proxy_pass + HTTP/1.1 Upgrade/Connection 头
                      (proxy_read_timeout 300s, proxy_buffering off)
   Spring Boot jar (systemd 托管, 127.0.0.1:8080)
   MySQL 8.0  (127.0.0.1:3306, 仅本机/内网)
```

80 端口强制 301 跳转 443；`/ws` 访问日志对 query_string 做脱敏（首帧认证后 URL 不含凭据，仅作纵深防御）。

### 11.2 配置管理与安全响应头

`application-{dev|prod}.yml` 分环境配置；生产密钥（JWT 密钥、数据库密码、Redis 密码）通过环境变量/启动参数注入，不提交仓库；日志 Logback 按天滚动、保留 30 天（应用日志）与 ≥180 天（审计，落库）。

Nginx 全局注入安全响应头（对应 9.1 信息泄露/注入对策）：

```nginx
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
add_header X-Content-Type-Options "nosniff" always;
add_header X-Frame-Options "DENY" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
add_header Content-Security-Policy "default-src 'self'; img-src 'self' data:;
  style-src 'self' 'unsafe-inline'; connect-src 'self' wss:; form-action 'self';
  object-src 'none'; base-uri 'self'; frame-ancestors 'none'" always;
  # style 内联为 Element Plus 运行时所需、connect-src 含 wss 供 WebSocket，均为已知权衡
```

**Nginx 限流（与 9.1 双层限流、7.2 降级兜底对应；完整示例见 `deploy/nginx/nginx.conf.example`）**：

```nginx
# 三桶（数值为全站唯一口径；超限一律 429，Nginx 默认 503 必须显式改）
limit_req_zone $binary_remote_addr zone=login_zone:10m  rate=10r/m;   # 登录
limit_req_zone $binary_remote_addr zone=borrow_zone:10m rate=30r/m;   # 申领
limit_req_zone $binary_remote_addr zone=scan_zone:10m   rate=120r/m;  # 扫码信息查询
limit_req_status 429;

location = /api/v1/auth/login        { limit_req zone=login_zone  burst=5  nodelay; ... }
location = /api/v1/borrows           { limit_req zone=borrow_zone burst=10 nodelay; ... }
location ~ ^/api/v1/bags/[^/]+/info$ { limit_req zone=scan_zone   burst=30 nodelay; ... }
```

超限由 Nginx 直接返回 429（不带业务错误码，前端按 429 统一提示）；**应用层限流仍返回既有业务码**（5101/4109 等），两者不混用。账号锁定（5 次失败锁 15 分钟）为账号维度，与按 IP 的 Nginx 桶互为补充。降级期（Redis 不可用）应用层限流退化为本三桶按 IP 兜底（键与阈值见 7.2 降级矩阵）。

**容量估算（2C4G 同配压测）**：JVM `-Xms1g -Xmx2g`；Tomcat `max-threads=200`；HikariCP `maximum-pool-size=20`；Redis `maxmemory 512mb`、`maxmemory-policy noeviction`（内存打满即写失败并触发 7.2 熔断降级，行为明确可测；弃用 volatile-lru 的理由见 8.3）；Nginx `worker_connections 10240`。并发性能压测（12.2）在与生产同配的云服务器执行，确保容量结论可直接迁移。

### 11.3 发布、备份与主机加固

- 发布：前端 `npm run build` 产物覆盖 dist 并 `nginx -s reload`；后端 jar 经 systemd 重启，健康检查 `GET /actuator/health`（仅内网）通过后切流量；保留上一版本 jar 一键回滚。
- 备份：MySQL 每日 mysqldump 全量 + binlog，保留 7 天；**备份文件 GPG 加密存储**（含明文手机号等敏感数据），调取登记，到期销毁；Redis 开启 AOF everysec。**审计数据归档导出物（7.5）按同一口径管理**——GPG 加密、调取登记、到期销毁。
- 密钥运维：JWT 密钥 ≥32 字节 CSPRNG 随机、双密钥轮换窗口（7.1）；数据库/Redis 口令强度要求同密码策略；**备份 GPG 私钥**（离线介质或独立托管，与备份文件分开存放，定期恢复演练；丢失则备份不可用、泄露则加密失效）与**收件人手机号 HMAC 密钥**（环境变量注入；轮换时对存量哈希做版本标记或重算，见 8.2）一并纳入密钥清单；泄露应急预案：轮换密钥 → 全量 token_version 自增 → 复查审计日志。
- SSH 加固：禁用口令登录（仅密钥）、限制来源 IP、禁用 root 直接登录。

### 11.4 监控与可用性口径

- Spring Boot Actuator 仅暴露 `/actuator/health`（内网，进程自身健康）；对外由 Nginx 将 `/api/health` 反代至该端点（免鉴权，见 6.3，仅返回存活状态），并以 1 分钟间隔拨测。
- **可用性口径**：统计周期内拨测成功次数 ÷ 总拨测次数，演示期（2027-04 起）月度可用率目标 ≥99%，超 SLA 记录故障与处置——以监控数据度量，而非定性承诺。

### 11.5 维护设计

- 日志分级与保留见 11.2；审计日志独立保留策略见 7.6。
- 常见运维要点（**固化于本节，不单独立册**——交付物清单不含《运维手册》，对应 NFR-MNT-04 口径）：Redis 熔断降级与恢复操作（7.2）、库存对账差异排查（R4 告警 → 盘点单 → 状态修正留痕）、token 轮换（11.3）、站点停用移交（5.3）、**审计数据归档清理**（7.5：独立运维账号月度执行，导出 → GPG 加密留存 → 校验后删除，导出物调取登记见 11.3）。
- 升级策略：向后兼容的接口变更才允许直接发布；破坏性变更走 `/api/v2` 或公告停机窗口；依赖升级按 9.7 漏扫流程。
