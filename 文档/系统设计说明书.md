## 1 引言

### 1.1 编写目的

本文档依据《本科毕业设计任务书》（2026-09-01 下发）及《需求规格说明书》，给出共享快递袋系统（英文名 **Shared Express Mailer System**，缩写 SEMS，开发阶段的工程目录与代码制品统一使用该名称）的总体架构、功能模块、核心业务流程、数据库概要结构、接口规范、关键技术方案与安全设计，作为后续编码实现、数据库详细设计、测试与部署的依据。

本文档的预期读者：指导教师、毕业生本人、答辩评审专家，以及后续参与系统实现与维护的开发人员。

### 1.2 项目背景

随着电子商务与快递业务规模持续增长，一次性快递包装消耗量大、回收率低。国务院《固体废物综合治理行动计划》（国发〔2025〕14 号）明确提出加快推进快递包装绿色转型。共享快递袋以循环复用方式替代一次性包装，但目前投放、取用、回收、消毒、复用等环节普遍依赖线下人工登记，存在**库存信息不透明、流转过程不可追溯、站点间调度依赖经验、损坏与遗失责任难以认定**四类突出问题。

本系统面向校园、社区、写字楼等快递集散场景，以共享快递袋为循环载体，通过信息化手段实现快递袋**分配、使用、回收、消毒、调度**的全流程在线管理，形成"取—用—还—洗—调"闭环，并结合网络空间安全专业方向落实认证、鉴权、审计等安全机制。

## 2 总体设计

### 2.1 设计目标

1. 实现快递袋"取—用—还—洗—调"全流程线上化，全程状态可追溯（每步流转写日志、留操作人）。
2. 高并发取袋场景下库存**不超发、不漏发**（Redis 原子扣减 + 同步补偿 + 对账兜底）。
3. 三类角色权限边界清晰，接口无越权，操作全程可审计。
4. 前端响应式适配 PC 与移动端，扫码取袋 / 还袋在手机端即可完成。

### 2.2 设计原则

| 原则                           | 落地方式                                                                                                                                             |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| 前后端分离                     | 前端 Vue 3 独立工程，后端只提供 RESTful API，交互为纯 JSON                                                                                           |
| 无状态服务                     | 服务端不保存会话，身份凭 JWT 携带，便于水平扩展                                                                                                      |
| 状态集中管控                   | 快递袋状态只允许经统一状态机组件流转，业务代码不得直接 UPDATE 状态字段；3.2 转移表是状态流转的**唯一权威**，正文其他章节与本表冲突时以本表为准 |
| 实物为锚                       | 可用库存与实物一致：袋离开"空闲"即不可领用，库存回补只发生在实物回归（扫码确认）时点                                                                 |
| 缓存优先                       | 库存读扣减走 Redis，MySQL 为权威底账，定时对账纠偏                                                                                                   |
| 安全内建（Security by Design） | 认证、鉴权、参数校验、审计以框架层切面/拦截器统一实现，不依赖各业务代码自觉                                                                          |
| 统一出口                       | 全局异常处理器 + 统一 JSON 响应体，前端只需处理一种响应结构                                                                                          |

### 2.3 系统总体架构

B/S 架构、前后端分离，自上而下分为五层（图 2-1）：

```
图 2-1 系统总体架构图
┌─────────────────────────────────────────────────────────┐
│ 客户端层                                                 │
│   PC 浏览器（管理端） / 移动端 H5（扫码取袋、还袋、订单） │
│   Vue 3 + Vite + Element Plus + Pinia + Axios + ECharts  │
└────────────────────────┬────────────────────────────────┘
                         │ HTTPS（JSON / WebSocket）
┌────────────────────────▼────────────────────────────────┐
│ 接入层  Nginx                                            │
│   静态资源托管(dist) · /api 反向代理 · /ws 升级代理       │
│   TLS 终结 · gzip · 安全响应头 · 限流兜底                 │
└────────────────────────┬────────────────────────────────┘
┌────────────────────────▼────────────────────────────────┐
│ 应用层  Spring Boot（单体分层，按模块分包，图 2-2）       │
│   过滤器/拦截器：JWT 认证 → RBAC 鉴权 → 数据权限注入      │
│   Controller（RESTful API）→ Service（业务/状态机/事务）  │
│   → Mapper（MyBatis-Plus）                               │
│   横切：@AuditLog 审计切面 · 全局异常 · 参数校验          │
│   WebSocket 推送服务（库存变动 / 订单状态变更）           │
│   定时任务：超时订单 · 库存对账 · 日统计                  │
└──────────────┬───────────────────────┬──────────────────┘
┌──────────────▼──────────┐ ┌──────────▼─────────────────┐
│ 数据层  MySQL 8.0        │ │ 缓存层  Redis 7            │
│   业务底账 · 流转日志     │ │   库存原子扣减(Lua)         │
│   审计日志               │ │   JWT 黑名单 · 预扣凭据(TTL)│
│   (权威数据源)           │ │   开单计数 · 限流 · 验证码   │
└─────────────────────────┘ └────────────────────────────┘
```

**架构决策说明：**

- **采用单体分层而非微服务**：系统业务规模为校园级（站点数 ≤ 数十、袋量 ≤ 万级、峰值并发申领为瞬时低频），微服务带来的注册中心、网关、链路追踪等复杂度远超收益；按模块分包保持清晰的逻辑边界，未来可平滑拆分。
- **Nginx 同时承担静态托管与反向代理**，前端构建产物与 API 同域，规避跨域复杂度（开发期由 Vite proxy 代理）。
- **WebSocket 推送服务内嵌于应用层**，不引入独立消息中间件；推送内容为轻量状态变更通知，单机 WebSocket 会话管理即可满足规模。

### 2.5 功能模块划分

按任务书划分为六大模块，与三类角色的关系如下：

```
共享快递袋系统
├── M1 用户管理 ──────────── 三类角色共用（注册/登录/个人中心；平台管理员可管理用户、
│                            创建账号并授予角色、绑定站点）
├── M2 共享快递袋服务 ────── 普通用户（扫码取袋、寄件登记、标记归还、我的订单）
├── M3 共享站点管理 ──────── 平台管理员（站点维护）；站点管理员（本站库存、回收箱、预警）
├── M4 快递袋管理 ────────── 站点管理员（激活上架、出入库、盘点、消毒登记、维修报废）；
│                            平台管理员（袋档案、二维码批量生成、状态修正）
```

### 2.7 关键设计决策记录

| 决策                   | 结论                                                                                | 主要理由与备选方案                                                                                                           |
| ---------------------- | ----------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 库存扣减位置           | Redis Lua 原子扣减为主，MySQL 行级条件更新兜底                                      | 备选"仅 MySQL 行锁/乐观锁"在并发取袋时热点行竞争明显；Redis + TTL 过期机制是任务书明确要求                                   |
| 架构形态               | 单体分层                                                                            | 备选微服务复杂度不匹配毕设规模（见 2.3）                                                                                     |
| 认证方案               | JWT（含 token_version）+ Redis 黑名单                                               | 纯 JWT 无法主动失效（登出/封禁/调岗即失效需求）；jti 黑名单解决单设备登出，用户级 token_version 解决封禁/重置/调岗的全量吊销 |
| RBAC 形态              | 三角色简化 RBAC（用户-角色两表 + 注解权限点），管理角色继承普通用户能力             | 角色固定且少，完整五表模型收益低；保留 user_role 关联表结构便于扩展                                                          |
| 站点管理员与站点的绑定 | `sys_user.station_id` 单站绑定（一岗一站）                                        | 满足"站点管理员限本站"的全部场景且实现最简；若未来需一人多站，升级为 user_station 多对多并让数据权限走 IN 集合，接口不变     |
| 袋的站点归属语义       | `bag.station_id` = **当前存放站点**，随回收确认、调拨入库等实物转移事件变更 | 备选"归属永不变化"将导致跨站归还账实分离（详见 3.2 表后说明）                                                                |
| 消息推送               | 原生 WebSocket + JSON 消息                                                          | 备选 STOMP/SockJS 协议较重；推送主题少且固定，原生更可控                                                                     |
| 订单与袋状态关系       | 袋状态为权威事实，订单状态跟随联动（联动表见 3.6）                                  | 避免双状态各自演化产生不一致；订单超时等由定时任务驱动                                                                       |
| 报废控制               | 站点管理员直接登记报废（留痕）+ 平台事后审计                                        | 备选"申请-审批流"需增设待复核状态与审批单据，超出毕设规模必要复杂度；报废本身已受状态机约束且全程留痕，审计可事后稽核        |

### 2.8 设计约束与假设

**约束（不可违背）**：技术栈按任务书固定（见 2.4）；单机部署（云服务器一台）；不对接第三方物流/支付接口，运单信息由用户手工录入；所有交付物使用中文。

**假设（设计依据，若不成立需重估）**：站点有人值守（站点管理员可执行扫码确认）；用户使用自己的手机扫码（微信内置浏览器或系统浏览器）；快递袋由站点货架自取、回收箱投递，无智能柜机硬件；系统不承担资金赔付自动执行，仅记录责任与处置结论。

## 3 核心领域设计：快递袋全生命周期状态机

### 3.1 状态定义

任务书规定生命周期为：空闲 → 已分配 → 使用中 → 回收在途 → 待消毒 → 可复用 →（维修/报废）。为支撑运营落地，将"维修/报废"细化为"维修中""报废"，并增设"未激活"（新袋上架前）、"调拨在途"（支撑"调"环节）、"已遗失"（支撑责任认定）三个运营态（图 3-1）：

```
图 3-1 快递袋状态图（主干）
                激活上架          扫码申领        提交寄件
  [未激活] ─────────────► [空闲] ──────────► [已分配] ──────────► [使用中]
                            ▲  ▲                │ │                   │
              上架入库       │  │ 未使用回收      │ │ 回收确认(直投)     │ 标记归还(可选)
        [可复用] ───────────┘  │                │ ▼                   ▼
                            │  │            [待消毒] ◄──回收确认── [回收在途]
              调拨入库       │  │                │ 消毒完成(合格)
        [调拨在途] ──────────┘  │                ▼
                            │  └──────────── [可复用]（形成循环）
  [维修中] ⇄ 可复用/待消毒/空闲（破损转入，修复回可复用，无法修复→报废）
  [已遗失] ◄─ 使用中/回收在途(遗失确认)、调拨在途(在途遗失确认)；找回→待消毒
  [报废]   终态
```

| 状态码       | 状态名   | 含义                                                 | 计入站点可用库存 |
| ------------ | -------- | ---------------------------------------------------- | ---------------- |
| INACTIVE     | 未激活   | 已建档案、已生成二维码，尚未贴标上架（新袋初始状态） | 否               |
| IDLE         | 空闲     | 已上架，可被申领                                     | 是               |
| ALLOCATED    | 已分配   | 用户扫码申领成功，尚未提交寄件信息                   | 否（已预扣）     |
| IN_USE       | 使用中   | 已寄件，处于寄送/使用环节                            | 否               |
| RETURNING    | 回收在途 | 用户已标记归还/已投放回收箱，待站点扫码确认          | 否               |
| TO_DISINFECT | 待消毒   | 回收确认完成，进入待消毒区                           | 否               |
| REUSABLE     | 可复用   | 消毒完成、检验合格，暂存待上架                       | 否               |
| TRANSFERRING | 调拨在途 | 处于站点间调拨运输中（扩展态）                       | 否               |
| REPAIRING    | 维修中   | 破损维修登记后（扩展态）                             | 否               |
| LOST         | 已遗失   | 超期未还/在途丢失，经平台管理员确认遗失（扩展态）    | 否               |
| SCRAPPED     | 报废     | 达到复用次数上限或无法修复，退出循环（终态）         | 否               |

> 站点可用库存的权威口径 = 该站点 IDLE 状态快递袋数量；Redis 计数与该口径对账（见 7.2 R4）。

**站点归属（`bag.station_id`）变更规则**：`bag.station_id` 语义为**当前存放站点**。变更仅发生在实物转移时点——#5/#7/#8 回收确认改为确认站点、#17 调拨入库改为目标站点、#20 找回改为找回登记站点、#21 修正时按需同步；登记站点在建袋/批量生成时指定（见 5.4），未激活期间即写入 `station_id`。#6 标记归还只在订单上记录 `return_station_id`，不改变袋归属。所有"限本站"校验按事件上下文比对操作人站点与该事件涉及的目标站点（见 4.4），而非无差别套用 `station_id=?` 过滤。

**非法跳变控制**：状态机组件仅注册上表 21 条合法转移；任何未注册的 (当前状态, 事件) 组合一律拒绝并抛出业务异常（错误码 4102），拒绝记录写入审计日志。转移执行采用"DB 条件 UPDATE（`WHERE status=前态 AND version=?`）"作为并发最后防线，防止两笔操作同时通过前置校验（如两人同时申领同一只袋）。

**#4 与 #5 的取用规则**：站点扫码后由系统按**绑定订单状态自动路由**，无需人工判断——订单已取消/不存在 → #4（袋回空闲）；订单仍为待寄件 → #5（进待消毒并关闭订单）。**平台管理员代操作**：表中"站点管理员（本站）"均含平台管理员全站代操作（前置校验不变、日志标记代操作），5.x 接口表中的"本站站点管理员"同理。**批量接口**（回收确认、消毒登记）逐只执行转移并返回逐袋结果明细，单只失败不影响其余。

**责任认定口径**：使用中遗失/回收在途超时 → 责任主体为申领用户；调拨在途遗失 → 责任主体为源站（由平台管理员裁决）；已分配留置超期 → 责任主体为申领用户。责任与处置结论在确认遗失时由平台管理员填写（`liability_record.responsible_user_id` 可空=责任待定，结论记于 `conclusion/decided_by/decided_at`，见 8.2）。

**订单级操作说明**：用户"撤回申领"与定时任务的"24h 超时取消"是**订单级操作**，只把订单置为已取消并删除预扣凭据，不改变袋状态（袋保持已分配，等待站点管理员执行 #4 未使用回收或 #5 回收确认）。订单状态定义见 3.6。

### 3.3 状态机实现设计

```text
BagStateMachine（唯一流转入口）
  fire(bagCode, event, operatorContext, clientRequestId)
    1. 幂等检查：以 clientRequestId + bagCode 查重（Redis SETNX，命中直接返回首次结果；
       批量接口逐袋独立幂等，接口入口的请求级幂等见 9.6）
    2. 查询袋当前状态（带乐观锁读取）
    3. 在转移注册表中查找 (currentState, event) → 转移规则
       未找到 → 抛 BizException(4102, "状态非法流转") + 记审计
    4. 执行前置校验（规则携带的 guard）：
       a. DB 校验：订单状态、归属、调拨明细、use_count 等
       b. Redis 原子校验（申领类）：未归还订单计数、取袋日频次、库存扣减与预扣凭据写入
          在同一个 Lua 脚本内一次完成（见 7.2），任一不满足则整体不落账
    5. 事务内：
       a. 条件 UPDATE bag SET status=目标, station_id=?, version=version+1
          WHERE code=? AND status=前态 AND version=?
          影响行数=0 → 并发冲突，终止（重复领取最后防线，报 4103）
       b. INSERT bag_transfer_log(...)
       c. 规则附带的业务动作（订单联动、Redis 库存增减、记录表写入等）
    6. 事务提交后：推送 WebSocket（库存/订单主题）
    7. 阶段一（申领）失败：库存已扣减而 DB 未落地时按 R0 同步补偿（INCR+DEL+计数回退）；
       库存未扣减（Lua 返回 0/-1/-2/-3/-4）时不回补库存，仅需回退进度类计数（见 7.2 失败分支矩阵）
```

事件与状态以 Java 枚举定义（`BagStatus`、`BagEvent`），转移注册表为静态 `Map<BagStatus, Map<BagEvent, TransitionRule>>`，新增流转只需注册规则，不改主流程。

#### 3.4.1 取袋—寄件流程（"取"与"用"，图 3-2）

```text

用户手机端          后端                      Redis            MySQL
  │ 扫袋上二维码      │                          │                │
  ├─────────────────►│ 校验JWT/袋状态=空闲       │                │

  │                  ├─ 事务: 建订单(待寄件) ────────────────────►│ 袋→已分配
```

并发说明：多笔申领并发时，Lua 脚本保证 Redis 扣减串行，余量不足者直接失败（4101）；DB 条件 UPDATE 保证同一只袋只绑定一个订单（4103，防重复领取）。两道防线独立生效。

#### 3.4.2 归还—消毒—复用流程（"还"与"洗"）

```text
主路径（站点扫码确认，不依赖用户任何操作）：
收件方拆件 → 将快递袋投放任一站点回收箱
  → 站点管理员清点回收箱，逐只扫码"回收确认"：
     袋 使用中/回收在途/已分配(未使用) → 待消毒（station_id 归入确认站点）
     对应订单：使用中/待回收确认 → 已完成（use_count+1，未归还订单计数 −1）；已分配 → 取消-回收闭环
     （站点扫码后系统按订单状态自动路由 #4/#5，见 3.2 表后说明）
辅助路径（可选，帮助站点提前感知）：
  → 用户端"标记归还"并选择投放站点：袋 使用中→回收在途，订单→待回收确认，
    站点工作台出现待办；超 72h 未确认纳入异常清单（见 3.5）
后续：按批次登记消毒（合格→可复用；不合格→维修中，维修后无法修复按 #14 报废）→ 上架入库（可复用→空闲，
     Redis+1，推送）。use_count 达上限的袋拒绝上架，提示转维修/报废（4108）。
```

#### 3.4.3 调拨流程（"调"）

```text
看板显示站点 A 库存低于预警阈值、站点 B 富余
  → 平台管理员创建调拨单(B→A, 数量N)，逐只扫码锁定明细袋（建单即锁定：
     取袋前置校验"袋未被未出库调拨单引用"）
  → B 站（源站）管理员执行调拨出库：袋 空闲→调拨在途，B 站库存 −N
  → 抵达后 A 站（目标站）管理员扫码核收入库：袋 调拨在途→空闲（归属改 A 站），
     A 站库存 +N，调拨单闭环
  → 出库后 48h 未核收 → 平台管理员确认在途遗失（袋→已遗失，调拨单异常，记责任）
异常处理：仅"待出库"状态的调拨单可整单取消，明细袋解锁回空闲；出库扫码失败
（实物缺失/码损）→ 将该袋从调拨单剔除（状态回空闲）后其余继续出库。
单据状态机：待出库 --首只出库--> 在途（未出库明细仍可继续出库或由平台剔除解锁）
→ 全部核收 --完成--> 已完成；部分核收/在途遗失确认后单据置"异常"并保留差异记录，
由平台管理员决定继续核收或终止（终止时未出库明细解锁回空闲）。
```

#### 3.4.4 库存盘点流程

站点管理员发起盘点 → 选择本站点 → 系统展示各状态账面数 → 录入各状态实际数 → 保存生成盘点单（差异自动计算）→ 有差异的单只袋由平台管理员按转移表 #21 修正状态并留痕（必填盘点单号与原因）。盘点单不可删除，仅可作废重盘。

### 3.6 订单状态设计

订单状态枚举 `OrderStatus`（订单表带 `version` 乐观锁与 `client_request_id` 幂等字段）：

| 订单状态        | 含义       | 对应袋状态                | 进入条件（事件）                                 |
| --------------- | ---------- | ------------------------- | ------------------------------------------------ |
| PENDING_SEND    | 待寄件     | 已分配                    | 扫码申领成功（转移#2）                           |
| IN_USE          | 使用中     | 使用中                    | 提交寄件（#3）                                   |
| PENDING_CONFIRM | 待回收确认 | 回收在途                  | 标记归还（#6）                                   |
| FINISHED        | 已完成     | （袋已进待消毒）          | 回收确认（#7/#8）                                |
| CANCELLED       | 已取消     | （袋保持已分配，待#4/#5） | 用户撤回 / 24h 超时取消 / 未使用袋回收确认（#5） |
| LOST            | 已遗失     | 已遗失                    | 平台管理员遗失确认（#18）                        |

- **"超时"不是订单状态**，是标记字段（`timeout_flag` + `timeout_time`）：寄件后 7 天未归还置位并推送提醒，状态仍为 IN_USE，直至归还或遗失确认。
- **未归还订单计数与订单状态同步**：订单进入 {待寄件, 使用中, 待回收确认} 时计数 +1，离开该三态（→已完成/已取消/已遗失）时计数 −1，与状态变更在同一事务/同一调用链内完成（见 7.2）。
- 订单状态与袋状态严格按上表联动，联动由状态机转移的伴随动作完成，不允许单独改订单状态。
- 并发保护：订单表 `version` 乐观锁 + 条件更新；`express_company + tracking_no` 联合唯一，防重复运单。

## 4 角色与权限设计（RBAC）

### 4.1 角色定义

| 角色       | 角色码         | 说明                                                                         |
| ---------- | -------------- | ---------------------------------------------------------------------------- |
| 普通用户   | USER           | 校园/社区/写字楼内取袋寄件、归还、查询本人订单的自然人                       |
| 站点管理员 | STATION_ADMIN  | 负责某一座站点运营的账号，通过`sys_user.station_id` 与站点绑定（一岗一站） |
| 平台管理员 | PLATFORM_ADMIN | 全局用户/站点/快递袋/订单管理、调拨调度、数据统计、审计查询、异常裁决        |

### 4.2 权限模型

采用简化 RBAC：`sys_user`（含 `status`、`station_id`、`token_version`）— `sys_user_role`（用户-角色关联）— `sys_role`（三行固定数据）。接口级权限点以后端注解 `@RequireRole("STATION_ADMIN")` 声明，由统一拦截器校验，不引入可配置权限表（角色固定，避免过度设计；如需扩展可平滑升级为"角色-菜单-权限点"五表模型）。

**账号与角色开通路径（初始管理员来源）**：初始化 SQL 预置一名平台管理员（首次登录强制改密）；之后由平台管理员在用户管理中**创建账号并授予角色**（`POST /users`），站点管理员创建时**必须绑定站点**（`PUT /users/{id}/station`），站点管理员的 `stationId` 由此写入并随 JWT 携带——这是 JWT 中 `stationId` 声明的唯一来源。调岗/换绑站点/角色变更时自增该用户 `token_version`，旧 token 立即失效（见 7.1）。

JWT 载荷携带 `uid、role、stationId（站点管理员专属）、tokenVersion、jti、exp`，拦截器一次解析即可完成认证与粗粒度鉴权。

### 4.3 角色—功能权限矩阵

**继承规则：站点管理员与平台管理员天然具备普通用户的全部业务能力**（取袋、寄件、标记归还、查询本人订单），且同样受"未归还订单 ≤3 单"与取袋频次约束。矩阵与 5.x 接口表的权限列冲突时，以接口表为准。平台管理员对站点类操作可**全站代操作**（前置校验不变、日志标记代操作）；5.x 权限列中"本站站点管理员"均含平台管理员代操作，"本人"为数据范围限定（非角色），"登录用户"含管理角色继承（见上）。

## 5 功能模块详细设计

> 接口统一前缀 `/api/v1`，下表仅列核心接口，完整签名（入参/出参/示例）随开发进度维护于接口文档（OpenAPI/Apifox）。响应结构与错误码见第 6 章。除特殊说明外，写操作均需携带 `clientRequestId` 幂等头（见 9.6）。

### 5.1 用户管理模块（M1）

## 6 接口设计规范

### 6.1 RESTful 约定

- 路径前缀 `/api/v1`，资源名用复数名词（`/bags`、`/orders`、`/stations`、`/users`），子资源用嵌套（`/stations/{id}/stock`）。
- 动词语义：GET 查询、POST 创建/触发动作、PATCH 部分更新、PUT 全量替换（角色授予、站点绑定等"整体替换"语义）、DELETE 删除/取消。动作型业务（如"回收确认""遗失确认"）采用 `POST /资源/动作` 形式。
- 查询参数：分页 `pageNum`（默认 1）、`pageSize`（默认 10，最大 100）、排序 `orderBy=field,asc|desc`（字段白名单）；时间区间 `beginTime/endTime`。
- 写操作幂等头：`clientRequestId`（客户端生成的 UUID），见 9.6。

### 6.2 统一响应格式

```json
{ "code": 0, "message": "success", "data": { } }
```

- `code=0` 表示成功；非 0 为错误码（见 6.4）。分页数据放在 `data.records / data.total / data.pages`。
- **例外**：`batch-generate` 的二维码 ZIP 下载为二进制流响应（`Content-Disposition` 附件下载），是统一 JSON 之外唯一声明的例外。
- **批量接口的部分失败**：逐袋执行的批量接口（回收确认、消毒登记）在 `data` 中返回逐袋结果明细（成功/失败 + 错误码），单只失败不影响其余；声明为"整批原子"的接口（batch-generate）单独标注；批量数量超限统一由 3001 承载。
- 所有异常由全局异常处理器转换为统一格式（处理链见 6.6）：参数校验失败（400）、未认证（401）、无权限（403）、业务异常（200 + 业务错误码）、系统异常（500，不向前端暴露堆栈）。

### 6.3 认证约定

除 `/auth/register`、`/auth/login`、`/auth/captcha` 与健康端点 `/api/health`（仅返回存活状态，不泄露内部信息）外，所有接口要求请求头 `Authorization: Bearer <JWT>`；`401` 前端清除本地 token 并跳转登录；`403` 提示无权限。

### 6.4 错误码表（核心）

| 错误码 | 含义                              | 典型场景                                                                        |
| ------ | --------------------------------- | ------------------------------------------------------------------------------- |

| 1001   | 未认证 / token 无效、过期或已吊销 | 未登录访问、jti 黑名单、token_version 不匹配                                    |

后端集成 springdoc-openapi 自动生成 OpenAPI 文档（生产环境关闭暴露）；接口发生变更时同步更新 Apifox 工程，任务书要求的"接口变更同步维护文档"以此落实为开发流程约束。

### 6.6 出错处理设计

| 异常类别                                           | 处理方式                 | 响应                           | 日志                            |
| -------------------------------------------------- | ------------------------ | ------------------------------ | ------------------------------- |
| 参数校验异常（MethodArgumentNotValidException 等） | 全局处理器汇总字段错误   | 400 + code 3001 + 字段错误明细 | WARN，不记参数值                |
| 业务异常（BizException，携带错误码）               | 正常业务分支             | 200 + 业务错误码               | INFO（4102/2002/2001 另记审计） |

## 7 关键技术方案设计

### 7.1 JWT 认证设计

- 载荷：`sub=uid`、`role`、`stationId`（站点管理员专属，来源见 4.2）、`tokenVersion`、`jti`（唯一 ID）、`iat`、`exp`；**解析侧固定 HS256**（拒绝其他 alg），密钥为 ≥32 字节 CSPRNG 随机串，从环境变量注入，不入库不入码，支持双密钥轮换窗口（旧密钥只验不签，过渡 24h）。
- 有效期：access token 2 小时；前端剩余 <30 分钟时调 `POST /auth/refresh` 静默续签（旧 jti 入黑名单）。
- **两级主动失效**：
  1. **单设备登出**：登出/续签时将 `jti` 写入 Redis 黑名单（key `auth:deny:{jti}`，TTL=token 剩余有效期）；
  2. **用户级全量吊销**：`sys_user.token_version`（禁用、重置密码、改密、调岗/换绑站点/改角色时自增），自增后同步 `DEL auth:userver:{uid}` 使缓存立即失效；拦截器比对 token 载荷中的版本与该值（Redis 仅作 60s 读加速）不一致即拒绝。被禁用账号的存量 token 在**下一次请求即被拒绝**，"封号即失效"由此兑现；WebSocket 通道在下次心跳（≤30s）断开。
- 拦截链：`OncePerRequestFilter` 解析 token → `HandlerInterceptor` 做 `@RequireRole` 鉴权 → Service 层数据权限校验（见 4.4）。
- 多端登录策略：允许多端同时在线（每端独立 jti）；登出仅失效当前端，全量失效靠 token_version。

### 7.2 Redis 库存并发扣减方案（防超发/漏发）

**语义约定**：可用库存 = 站点 IDLE 袋数，DB 为权威、Redis 为读写视图；库存回补只发生在实物回归（扫码确认）时点（见 2.2 "实物为锚"）。业务取消时限统一为 24h（见 3.5），预扣凭据 TTL 25h 仅作凭据。

**数据结构**

| Key                               | 类型         | TTL            | 说明                                                                                                      |
| --------------------------------- | ------------ | -------------- | --------------------------------------------------------------------------------------------------------- |
| `stock:available:{stationId}`   | String(int)  | 无（对账维护） | 站点可用库存计数                                                                                          |
| `stock:hold:{orderNo}`          | String(json) | 25h            | 预扣凭据（orderNo/stationId/bagCode），**不承担取消语义**；供 R0/R1/R2 删除与 R3 启动期孤儿检查读取 |
| `stock:init:{stationId}`        | String(标记) | 300s           | 计数初始化互斥标记（SETNX，防惊群）                                                                       |
| `stock:reconcile:{stationId}`   | String(标记) | 120s           | 对账互斥标记（对账期间扣减请求短暂重试）                                                                  |
| `borrow:open:{uid}`             | String(int)  | 14 天滑动      | 未归还订单计数（≤3，原子校验；进入三态 +1、离开三态 −1）                                                |
| `borrow:daily:{uid}:{yyyyMMdd}` | String(int)  | 当日+1天       | 取袋日频次计数（≤10）                                                                                    |

**Lua 原子扣减脚本**（申领时执行，"检查-扣减-记录"三步原子化，防超发）：

```lua
-- KEYS[1]=stock:available:{sid}  KEYS[2]=stock:hold:{orderNo}  KEYS[3]=stock:reconcile:{sid}
-- KEYS[4]=borrow:open:{uid}      KEYS[5]=borrow:daily:{uid}:{yyyyMMdd}
-- ARGV[1]=预扣凭据JSON  ARGV[2]=凭据TTL秒  ARGV[3]=open上限  ARGV[4]=daily上限  ARGV[5]=daily TTL秒
if redis.call('EXISTS', KEYS[3]) == 1 then return -2 end   -- 对账中，客户端短暂重试
local avail = tonumber(redis.call('GET', KEYS[1]) or '-1')
if avail == -1 then return -1 end                          -- 计数未初始化 → 5102
if tonumber(redis.call('GET', KEYS[4]) or '0') >= tonumber(ARGV[3]) then return -3 end  -- 未归还订单超限 → 4104
if tonumber(redis.call('GET', KEYS[5]) or '0') >= tonumber(ARGV[4]) then return -4 end  -- 取袋频次超限 → 4109
if avail < 1 then return 0 end                             -- 库存不足 → 4101
-- 以下四步在同一脚本内原子完成；前面任一检查未通过则整体不落账
redis.call('DECR', KEYS[1])                                -- 库存扣减
redis.call('SETEX', KEYS[2], ARGV[2], ARGV[1])             -- 预扣凭据
redis.call('INCR', KEYS[4])                                -- 未归还订单计数
redis.call('INCR', KEYS[5])                                -- 取袋日频次
redis.call('EXPIRE', KEYS[5], ARGV[5])
redis.call('EXPIRE', KEYS[4], 1209600)                     -- 计数 TTL 14 天滑动续期
return 1
```

**两阶段流程与五条回补路径（R0–R4）**

```text
阶段一 预扣:  单个 Lua 原子完成「未归还订单计数<3 + 取袋日频次<10 + 库存 DECR + 写预扣凭据」
              → DB事务(建订单PENDING_SEND + 袋条件UPDATE→已分配 + 流转日志)
              ├─ 成功 → 返回订单号
              └─ 失败(含同袋竞争4103/宕机前检测到的任何异常) → R0
阶段二 确认:  提交寄件 → DB事务(订单→使用中 + 袋→使用中) → DEL 预扣凭据

Lua 返回值与失败分支矩阵（实现时逐条对应）：
  1=成功；0=库存不足(4101)；-1=计数未初始化(5102，可重试)；
  -2=对账中(短暂重试，沿用同一 clientRequestId)；-3=未归还订单超限(4104)；-4=取袋频次超限(4109)
  · Lua 返回 0/-1/-2/-3/-4 → 库存未扣减、计数未自增，**不回补库存**，仅按需重试
  · Lua 成功但 DB 事务失败 → R0：INCR 库存 + DEL 预扣凭据 + 未归还订单计数 −1
    （日频次不退还，符合 3.5"含已撤回/已取消"口径）
  · Lua 成功后进程崩溃（无同步补偿机会）→ 计数漂移由 R4（≤30 分钟）与每日开单计数对账纠正

R0 同步补偿（主路径，必需分支）: 阶段一 DB 事务失败时，在同一请求内
    INCR 库存 + DEL 预扣凭据 + 未归还订单计数 −1，写 stock_compensation_log
    （幂等键=clientRequestId，防止与 R1-R4 重复回补）；补偿失败则记 ERROR 告警，
    交由 R3 兜底。
R1 用户撤回:  订单置已取消（未归还订单计数 −1），DEL 预扣凭据；**不回补库存**
    （实物仍在用户手上），袋保持已分配，等待站点 #4 未使用回收（扫码时 +1）。
R2 24h 超时取消（定时任务扫 DB，而非扫 Redis）: 订单 PENDING_SEND 且
    created_at 超过 24h → 置已取消，同 R1；袋仍在站时由站点 #4 收回。
R3 崩溃窗口兜底: 进程在 Lua 扣减后、DB 事务前宕机 → 无订单行、预扣凭据成孤儿。
    应用启动时扫描 stock:hold:* 与 DB 订单比对（启动期一次性，量小）：
    孤儿凭据 DEL 并记告警；计数由 R4 按 DB（IDLE 袋数）纠偏。
R4 定时对账（每30分钟）: 逐站点 SETNX stock:reconcile:{sid}（TTL 120s）
    → 间隔 1s 连续两次读 DB COUNT(IDLE)，两次一致才继续（降低与在途请求相撞）
    → SET 写回 Redis（不设 TTL）→ DEL 标记。
    对账期间扣减请求命中标记返回 -2，客户端 200ms 退避重试 3 次；
    差异写入告警日志。残余竞态（已过 Lua、尚未提交 DB 的在途扣减）最迟被
    下一轮对账收敛，且"同一只袋不被两人领取"由 DB 条件 UPDATE 独立保证。
```

**DB 兜底**：袋表条件 UPDATE（`WHERE code=? AND status='IDLE' AND version=?`）是重复领取的最后防线；Redis 故障时的**降级路径**见下。

**计数初始化与故障恢复**：应用启动及 Redis 故障恢复时，逐站点 `SETNX stock:init:{sid}` 后按 `COUNT(IDLE)` 重建计数；初始化完成前该站点的申领请求返回 5102（可重试）。**降级触发**：连续 3 次 Redis 命令异常（10s 窗口）→ 熔断打开，申领直走 DB 行级路径（按袋码锁定行并条件 UPDATE，并发正确性由行锁保证，仅损失吞吐）；Redis 恢复探测通过后走初始化流程重建计数并关闭熔断。降级期间不写 Redis 计数，避免恢复后计数偏高。初始化由启动/恢复事件单线程触发，`COUNT=0` 也写入 0 值，初始化失败由 R4 兜底并告警。

**降级期各项 Redis 依赖控制的行为**（不得静默放行）：

| 控制项                           | Redis 故障/熔断期行为                                                                        |
| -------------------------------- | -------------------------------------------------------------------------------------------- |
| 库存扣减                         | 走 DB 行级路径（按袋码条件 UPDATE），正确性由行锁保证                                        |
| 未归还订单 ≤3 / 取袋日频次 ≤10 | 退化为 DB 计数校验（COUNT 三态订单数 / COUNT 当日订单数，走`(user_id,status)` 与时间索引） |
| 幂等（clientRequestId）          | 由`bag_order.client_request_id` 与 `stock_compensation_log` 唯一键兜底                   |
| jti 黑名单（单设备登出）         | fail-closed：降级期拒绝该用户 token（或查 DB 兜底），不因 Redis 不可用而放行                 |
| token_version（禁用/重置/调岗）  | 不受影响（权威在 DB，Redis 仅 60s 读缓存）                                                   |
| 登录失败锁定 / 应用层限流        | 退化为 Nginx 层限流兜底，恢复后重置计数                                                      |
| 恢复动作                         | 重建`stock:available`、`borrow:open`、`borrow:daily` 后关闭熔断                        |

**防重复领取**：Redis 扣减解决"库存数量"并发；"同一只袋不被两人拿走"由 DB 条件 UPDATE 保证，两道防线独立生效。

**并发目标**：单站点 500 并发申领压测下，成功数 = min(请求数, 库存数)，无超发、无漏发（验证方法见 12.2）。

### 7.3 WebSocket 实时推送设计

- 端点：`/ws`。**认证采用首帧鉴权**（避免 token 进 URL 与 Nginx 访问日志）：连接建立后 10 秒内发送 `{"type":"auth","token":"<JWT>"}`，服务端校验通过方可订阅；超时或校验失败即断开。
- 订阅授权（服务端按 JWT 声明生成订阅白名单，越权订阅直接拒绝并审计）：

| 主题                     | 允许订阅方               | 推送时机                                                                         |
| ------------------------ | ------------------------ | -------------------------------------------------------------------------------- |
| `station/{id}/stock`   | 该站点管理员、平台管理员 | 可用库存增减（申领 −1；未使用回收/上架入库/调拨入库 +1；报废出库/调拨出库 −1） |
| `station/{id}/recycle` | 该站点管理员、平台管理员 | 用户标记归还（提醒确认）                                                         |
| `user/{uid}/order`     | 仅 uid 本人              | 订单状态变更、超时提醒                                                           |
| `platform/dashboard`   | 仅平台管理员             | 全局库存/订单异动、预警触发                                                      |

- 消息格式：`{"topic":"...","type":"...","data":{...},"ts":...}`。
- **连接期失效复查**：心跳（ping/pong，30s）时复用 HTTP 侧校验逻辑（jti 黑名单 + token_version + 账号状态），任一失效即主动断开——禁用/调岗用户的推送通道同步失效。
- 会话管理：`ConcurrentHashMap<主题, Set<Session>>`；推送在业务事务提交后触发（`TransactionSynchronization.afterCommit`），避免"事务回滚但消息已发"。
- 前端：断线指数退避重连（1s/2s/4s/…上限 30s）；`visibilitychange` 回前台立即重连并**重新拉取当前页数据**兜底（不上消息 ACK/重放机制）。

### 7.4 快递袋编码与二维码方案

- **编码规则**：`SJB-{规格码1位}-{出厂年月yyMM}-{5位流水}-{1位校验码}`，示例 `SJB-L-2609-00001-7`。流水段连续、末位校验码（模 31 混淆算法）用于拦截手输错误与提高枚举成本；**编码不承载站点语义**（原"站点归属预留段"取消），归属一律以 `bag.station_id` 为准。
- **二维码内容**：`https://{域名配置}/m/bag/{bagCode}`（域名由配置项注入，变更域名后旧二维码需换标重印，或在旧域名保留 301 跳转；域名不参与编码与签名），微信"扫一扫"可直接打开袋详情/申领页；系统内扫码先调 `GET /bags/{bagCode}/info` 校验袋码存在性与状态合法性（未激活/报废/遗失返回 4107 并提示）。
- **信息最小化（防枚举）**：`info` 接口对与操作人无归属关系的袋仅返回"规格 + 是否可领用 + 所在站点名称"；同一用户 1 分钟内 ≥10 次袋码查询失败 → 触发 5101 限流并记审计（风控线索）。
- **生成**：后端 ZXing 批量生成 PNG（含编码文本下方标注），打包 ZIP 供平台管理员下载打印；打印贴标前袋为"未激活"，首次激活上架（转移 #1）后进入循环。
- **识别**：移动端 H5 使用浏览器 `BarcodeDetector` API，不支持的浏览器降级引入 jsQR；站点管理员可使用 USB 扫码枪（等价键盘输入袋码），移动端提供袋码手输入口兜底。
- **防伪边界**：二维码为明文 URL、不做密码学签名——仿制标签**无法绕过**服务端状态机、归属校验与唯一约束，其危害限于"引导用户打开错误落地页"；异常扫码地点/频次作为审计线索（见 9.1 威胁条目）。**真标换贴**（把 A 袋标签贴到 B 袋）服务端无法检测，属已认领的残余风险，依靠回收/上架外观与数量核验、盘点差异、流转地点与时间异常审计发现（见 3.4.4）。

### 7.5 定时任务设计

统一约定：调度使用独立线程池（4 线程）；每任务声明幂等键、执行超时（5 分钟）、失败告警；扫描类任务分批（LIMIT 500）+ 命中索引，禁止全表扫描。

| 任务                   | 频率       | 幂等依据                      | 逻辑                                                                                                           |
| ---------------------- | ---------- | ----------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 超时订单扫描           | 每 5 分钟  | 订单状态机（取消幂等）        | 24h 未寄件自动取消（R2）；寄件后 7 天置超时标记并推送提醒；取消后 48h 袋仍为已分配的纳入异常看板告警（见 3.5） |
| 回收/调拨超时扫描      | 每 15 分钟 | 状态机幂等                    | 回收在途 24h 提醒 / 72h 纳入异常；调拨出库 48h 未核收提示在途遗失确认                                          |
| 库存对账               | 每 30 分钟 | `stock:reconcile` 互斥标记  | R4：Redis 与 DB 库存比对修正，差异告警                                                                         |
| 开单计数对账           | 每日 02:00 | 计数键重置                    | `borrow:open:{uid}` 与 DB 未归还订单数比对修正                                                               |
| 日统计汇总（可选优化） | 每日 01:00 | `(date, station_id)` 唯一键 | 汇总订单量、周转率、库存分布入 stats_daily                                                                     |

实现采用 Spring `@Scheduled` 单机调度（单实例部署无需分布式锁；如未来多实例，以 Redis `SETNX` 抢占锁，方案已预留）。

### 7.6 操作日志与审计

- 注解 `@AuditLog(module="快递袋管理", action="消毒登记")` 标注在 Controller 方法上，AOP 环绕采集：操作人、角色、IP、UA、模块/动作、入参（**密码等敏感字段脱敏后**再记录）、结果（成功/失败+错误码）、耗时。登录失败、越权拦截（2001/2002）、状态机拒绝（4102）、报废与状态修正、**回收确认（含跨站与未标记直投）**等关键事件**必须**入审计。
- 异步落库（独立线程池 + 有界队列）与**队列饱和策略**：队列满时——关键事件降级为同步写；普通事件写入本地应急文件（启动时回放入库）并累加丢弃计数器（落库并在 5.6 看板告警、另写 ERROR 日志），确保审计写入高峰（往往正是攻击高峰）不拖垮业务、也不静默丢失。
- 防篡改三层：①应用层不提供审计表的修改/删除接口；②**数据库账号对 `audit_log / login_log / stock_compensation_log` 仅授予 INSERT、SELECT**；③保留期 ≥180 天，备份加密存储（见 11.3）。
- 审计查询仅平台管理员可见（见 5.6）。

## 9 安全设计（网络空间安全方向重点）

### 9.1 威胁分析与对策总览

| 威胁                        | 对应风险                                   | 设计对策                                                                                                                                               |
| --------------------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 身份伪装（Spoofing）        | 弱口令、token 被盗用                       | BCrypt 强哈希、失败锁定、验证码、JWT 短有效期+两级吊销（jti 黑名单 + token_version）、HTTPS 传输                                                       |
| 篡改（Tampering）           | 越权改单、恶意参数                         | 服务端状态机校验、参数校验（JSR-380）、乐观锁、预编译防注入                                                                                            |
| 抵赖（Repudiation）         | 操作后不承认                               | 全量审计日志（IP/UA/参数/结果）应用层只插不改 + 数据库账号仅授 INSERT/SELECT，保留≥180 天                                                             |
| 信息泄露（Info Disclosure） | 越权查询他人订单、敏感数据外泄             | 水平越权校验、手机号脱敏、袋信息最小化返回（7.4）、最小化采集（不采集身份证）、错误信息不暴露堆栈                                                      |
| 拒绝服务（DoS）             | 登录/取袋/扫码接口被刷                     | Nginx+应用层双重限流、验证码升级、有界队列异步审计                                                                                                     |
| 权限提升（Elevation）       | 普通用户调用管理接口                       | 三层防线：拦截器注解鉴权 → Service 归属校验 → 状态机终审                                                                                             |
| 二维码伪造/克隆             | 换标、仿制落地页                           | 仿制标签无法绕过服务端状态机、归属校验与唯一约束；编码含校验位提高枚举成本；袋信息最小化；异常扫码频次/地点审计追溯                                    |
| 业务逻辑滥用                | 扫码刷袋、恶意占袋、撤回循环               | 未归还订单 ≤3（原子计数）、取袋 10 次/日、失败查询限流、撤回仅置订单取消不回补库存                                                                    |
| 内部人员舞弊                | 违规报废、修正状态、篡改盘点、异常回收确认 | 报废/状态修正/回收确认（含跨站与未标记直投）强制留痕并列入审计重点核查项；同类高频确认与流转异常触发看板告警；盘点差异单据支撑；审计表数据库层只插不改 |

### 9.2 认证与会话安全

- 密码策略：长度≥8 且含两类字符；BCrypt（cost 10）存储；传输仅经 HTTPS。
- 登录防护：同账号 5 次失败锁 15 分钟（`login:fail:{phone}`）；锁定后需图形验证码；登录成功/失败均写 `login_log`。
- 会话：access token 2h + 静默续签（7.1）；登出（jti 黑名单）、禁用/重置/调岗（token_version）**立即失效**；多端策略见 7.1。

### 9.3 访问控制（防越权）

- **垂直越权**：`@RequireRole` 注解 + 拦截器统一校验，管理接口在 Controller 层即拒绝普通用户。
- **水平越权**：三类强制校验——①订单类接口 `user_id` 一律取自 token，不接受前端传参；②站点管理员接口按**事件上下文站点**校验（见 4.4，含跨站归还的回收确认特例）；③按 id/编码取详情后再做一次归属比对（兜底）。
- **状态机终审**：即便权限与归属通过，非法状态转移仍被状态机拒绝（如站点管理员不能把一只"空闲"的袋确认为已回收——它根本不在回收流程中）。

### 9.4 注入与输入安全

- SQL 注入：MyBatis-Plus 全程预编译 `#{}`；代码规约禁止 `${}` 字符串拼接（排序字段等动态项用白名单映射）。
- 参数校验：Controller 入参 `@Validated` + JSR-380 注解（长度/格式/范围），袋码正则 `^SJB-[A-Z]-\d{4}-\d{5}-[0-9A-Z]$` 统一校验，防止任意字符串透传（前端校验规则见 10.4，后端为权威）。
- XSS：系统无富文本场景，响应头叠加 CSP（见 11.2）收窄注入面；会话不走 Cookie（JWT），降低会话劫持面。
- CSRF：无 Cookie 会话 + token 走 `Authorization` 头，天然免疫常规 CSRF；生产环境同域部署，CORS 默认关闭。

### 9.5 数据安全与脱敏

| 数据         | 存储                           | 展示                                |
| ------------ | ------------------------------ | ----------------------------------- |
| 登录密码     | BCrypt 摘要                    | 不可见                              |
| 手机号       | 明文（业务必需）               | `138****1234`；审计日志中同样脱敏 |
| 收件人手机号 | 掩码 + HMAC-SHA256 哈希（8.2） | 仅掩码；核对时比对哈希              |
| 运单号       | 明文                           | 归属人可见；他人不可查              |

传输全程 TLS 1.2+（Nginx 终结）；数据库账号按最小权限授权（应用账号不授予 DROP/GRANT，审计表仅 INSERT/SELECT）；云服务器安全组仅放行 22/80/443（SSH 见 11.3 加固），MySQL/Redis 仅监听内网，Redis 设置 requirepass。

### 9.6 接口防护

- 限流：登录、取袋、扫码信息查询接口以 Redis 固定窗口限流（如 10 次/分钟/用户），超限返回 5101。
- **幂等**：写操作统一携带 `clientRequestId`（客户端 UUID，服务端校验格式）请求头；服务端以 `idempotent:{uid}:{api}:{clientRequestId}` 为键去重（TTL 10min），命中已完成记录返回首次结果，命中"处理中"占位返回可重试提示。**幂等键粒度**：接口级幂等作用于请求入口；批量接口（回收确认、消毒登记）与状态机内部转移按 `clientRequestId + bagCode` **逐袋幂等**，避免第 2 只袋被误判为重复请求。重复申领另由"袋状态守卫 + DB 条件 UPDATE"兜底；取袋链路的库存扣减以 `clientRequestId` 为补偿幂等键（7.2 R0）。
- 上传：本系统无必需文件上传（二维码由系统生成），不开放用户上传功能。

### 9.7 供应链与依赖安全

Maven 侧接入 OWASP Dependency-Check、前端接入 `npm audit`，纳入构建流程；发现高危（CVSS ≥9）依赖时评估升级或替换并记录处置结论——作为网络空间安全方向的工程实践项。

**版面与交互要点**

- 用户端 H5：单列卡片流，页边距 16px，底部 Tab + 悬浮扫码主按钮（热区 ≥44px）；>768px 时居中为 480px 窄栏。
- 扫码与归还用**全屏结果卡**反馈：成功绿、失败红，配文案与提示音；确认键高 48px 并二次确认。
- 订单与袋卡片：状态标签置顶 + 左侧 4px 语义色条，关键字段两行内，主操作右对齐。
- 站点端 PC：顶部常驻扫码输入框，表格行高 48px、行内操作不超过 2 个，回收与消毒走抽屉，提交后即时刷新行状态。
- 站点端手机：入库、消毒确认为全屏单任务页，按钮高 48px 大字，适配手持工位。
- 平台端 PC：240px 深色 `#1E293B` 侧边栏 + 白卡内容区；>1200px 常驻，768–1200px 收为 64px 图标条。
- 看板：KPI 四列卡（数字 28px），网格线 `#E2E8F0`，图例常驻并直接标注，列数 4→2→1 自适应；轴标 12px 次要色，tooltip 白底浮层，数字用 `tabular-nums` 对齐。
- 响应式：<768px 全站单列，**表格一律转为卡片列表（禁止横向滚动）**，看板列堆叠、侧边栏转底部导航。
- 移动端安全区：底部固定元素加 `env(safe-area-inset-bottom)`，容器高度用 `100dvh`；键盘弹起时底部操作栏隐藏或上推。

**袋码展示与流转时间线**（两项容易被忽略但直接在答辩中被看到）

- 袋码与二维码：袋详情卡二维码渲染尺寸 ≥160px、静区 ≥4 个模块，袋码用等宽字体展示并可一键复制，附打印视图（批量打印见 7.4）；扫码页含取景框、手输兜底入口与"已扫到"的即时反馈（见 10.3）。
- 流转时间线：袋与订单详情页用 Timeline 组件呈现全生命周期闭环——每个节点按本节状态色着色，当前态高亮，异常节点（报废/遗失/超时）标红并附原因，节点信息含**操作人、站点、时间与流转日志摘要**。这是"取—用—还—洗—调"闭环最直观的展示位，不得省略。

**空态、加载与异常态**（缺一即显廉价，逐页落实）

- 加载：列表/卡片/看板三档骨架屏，**占位尺寸与真实内容一致**，不得用整页 spinner 造成跳版。
- 空态：插画或图标 + 一句说明 + 主操作按钮（如"暂无待回收袋" + "去扫码"）。
- 错误态：网络失败给"重试"按钮（对应 5102），403/404 给专属页面而非空白。
- 状态双通道：绿色系标签必须带图标，全站状态标签在红绿色盲模拟下逐屏自查，红绿不得相邻。

**禁止事项（美观底线）**

1. 禁止在页面或组件内写死颜色十六进制，一切走 CSS 变量；
2. 禁止超过三种圆角，禁用大圆角、重阴影、渐变等消费级风格；
3. 禁止仅靠颜色区分状态，必须"色 + 文案"（必要时加图标）；
4. 禁止图表使用色板外的高饱和彩虹色，饼图不超过 3 类；
5. 禁止绕过变量直接使用 Element Plus 原生冷灰与默认亮阶；
6. 禁止以 info 灰作可点击色——可点击元素一律用主色蓝；
7. 禁止新增或调换语义色与快递袋状态的映射关系（本节即权威口径）；
8. 本项目**不做整站深色模式**（深色仅用于平台端侧边栏），全局声明 `color-scheme: light`，避免系统暗色偏好反色破坏已校验的对比度。

## 11 部署设计

### 11.1 部署拓扑（云服务器）

```text
图 11-1 部署拓扑
Internet ──► 安全组(22/80/443)
   Nginx 443(TLS)
     ├── /          → /usr/share/nginx/html (Vue dist, SPA history 回退 index.html)
     ├── /api/      → proxy_pass http://127.0.0.1:8080  (Spring Boot)
     └── /ws        → proxy_pass + HTTP/1.1 Upgrade/Connection 头
                      (proxy_read_timeout 300s, proxy_buffering off)
   Spring Boot jar (systemd 托管, 127.0.0.1:8080)
   MySQL 8.0  (127.0.0.1:3306, 仅本机/内网)
   Redis 7    (127.0.0.1:6379, requirepass)
```

80 端口强制 301 跳转 443；`/ws` 访问日志对 query_string 做脱敏（首帧认证后 URL 不含凭据，仅作纵深防御）。

### 11.2 配置管理与安全响应头

`application-{dev|prod}.yml` 分环境配置；生产密钥（JWT 密钥、数据库密码、Redis 密码）通过环境变量/启动参数注入，不提交仓库；日志 Logback 按天滚动、保留 30 天（应用日志）与 ≥180 天（审计，落库）。

Nginx 全局注入安全响应头（对应 9.1 信息泄露/注入对策）：

```nginx
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
add_header X-Content-Type-Options "nosniff" always;
add_header X-Frame-Options "DENY" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
add_header Content-Security-Policy "default-src 'self'; img-src 'self' data:;
  style-src 'self' 'unsafe-inline'; connect-src 'self' wss:; form-action 'self';
  object-src 'none'; base-uri 'self'; frame-ancestors 'none'" always;
  # style 内联为 Element Plus 运行时所需、connect-src 含 wss 供 WebSocket，均为已知权衡
```

**容量估算（2C4G 同配压测）**：JVM `-Xms1g -Xmx2g`；Tomcat `max-threads=200`；HikariCP `maximum-pool-size=20`；Redis `maxmemory 512mb`（volatile-lru）；Nginx `worker_connections 10240`。并发性能压测（12.2）在与生产同配的云服务器执行，确保容量结论可直接迁移。

### 11.3 发布、备份与主机加固

- 发布：前端 `npm run build` 产物覆盖 dist 并 `nginx -s reload`；后端 jar 经 systemd 重启，健康检查 `GET /actuator/health`（仅内网）通过后切流量；保留上一版本 jar 一键回滚。
- 备份：MySQL 每日 mysqldump 全量 + binlog，保留 7 天；**备份文件 GPG 加密存储**（含明文手机号等敏感数据），调取登记，到期销毁；Redis 开启 AOF everysec。
- 密钥运维：JWT 密钥 ≥32 字节 CSPRNG 随机、双密钥轮换窗口（7.1）；数据库/Redis 口令强度要求同密码策略；**备份 GPG 私钥**（离线介质或独立托管，与备份文件分开存放，定期恢复演练；丢失则备份不可用、泄露则加密失效）与**收件人手机号 HMAC 密钥**（环境变量注入；轮换时对存量哈希做版本标记或重算，见 8.2）一并纳入密钥清单；泄露应急预案：轮换密钥 → 全量 token_version 自增 → 复查审计日志。
- SSH 加固：禁用口令登录（仅密钥）、限制来源 IP、禁用 root 直接登录。

### 11.4 监控与可用性口径

- Spring Boot Actuator 仅暴露 `/actuator/health`（内网，进程自身健康）；对外由 Nginx 将 `/api/health` 反代至该端点（免鉴权，见 6.3，仅返回存活状态），并以 1 分钟间隔拨测。
- **可用性口径**：统计周期内拨测成功次数 ÷ 总拨测次数，演示期（2027-04 起）月度可用率目标 ≥99%，超 SLA 记录故障与处置——以监控数据度量，而非定性承诺。

### 11.5 维护设计

- 日志分级与保留见 11.2；审计日志独立保留策略见 7.6。
- 常见运维手册项：Redis 熔断降级与恢复操作（7.2）、库存对账差异排查（R4 告警 → 盘点单 → 状态修正留痕）、token 轮换（11.3）、站点停用移交（5.3）。
- 升级策略：向后兼容的接口变更才允许直接发布；破坏性变更走 `/api/v2` 或公告停机窗口；依赖升级按 9.7 漏扫流程。
