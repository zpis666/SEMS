## 三、值得肯定的设计（均有代码证据）

以下各项建议在答辩 PPT 与论文"系统实现"章节中主动展示，不要等老师问。

### 3.1 状态机是唯一写入口，不是文档里的状态机

- `backend/src/main/java/com/sems/module/statemachine/TransitionRegistry.java:28-100` 静态注册 21 条规则，`register()` 用 `putIfAbsent` 检测重复，重复注册启动即失败（`:95-100`）。
- `BagTransitionService.java:281-292` 用 `WHERE bag_code=? AND status=前态 AND version=?` 双条件 UPDATE，影响行数为 0 即抛 4103。
- 流转前 `FOR UPDATE` 加载（`:215`），并在当前读下复核调拨锁定（`:155-159`）；注释说明了为什么不能只靠乐观锁插件。
- 21 条规则与《系统设计说明书》3.2 状态转移表逐条对应，`BagTransitionServiceTest` 23 项 + `TransitionRegistryTest` 8 项覆盖。

**答辩价值**：这是全项目最硬的技术亮点，能同时回答"如何防非法跳变""如何防重复领取""如何保证并发正确性"三个问题。

### 3.2 库存扣减是单脚本真原子

`backend/src/main/resources/lua/stock_deduct.lua:4-18` 把以下七步放在**同一个 Lua 脚本**内原子完成：

1. 计数初始化标记检查（未就绪 → `-1` → 5102）
2. 对账标记检查（对账中 → `-2` → 5103）
3. 可用库存读取与存在性判断
4. 在持袋数上限检查（超限 → `-3` → 4104）
5. 取袋日频次上限检查（超限 → `-4` → 4109）
6. 库存不足判断（`0` → 4101）
7. `DECR` 库存 + `SETEX` 预扣凭据 + `INCR` 在持数 + `INCR` 日频次 + 续期

失败码与业务码一一对应，见 `StockService.java:245-261`。**"检查与扣减在同一原子单元内"是防超发的根本原因**，比"先查再扣 + 加锁"更简洁。

### 3.3 失败后如何收敛的设计是完整的

| 机制 | 位置 | 作用 |
| --- | --- | --- |
| R0 同步补偿 | `StockService.java:284-305` | 以预扣凭据存在性做幂等，`DEL + INCR库存 + DECR在持` 在一个 Lua 内完成 |
| R3 启动清理 | `job/StartupRunner.java` | 清理上次进程退出遗留的孤儿凭据 |
| R4 周期对账 | `job/StockReconcileJob.java:149-190` | 每 30 分钟，**间隔 1 秒连续两次 `COUNT(IDLE)` 一致才写回**，避免把瞬时值固化 |
| 熔断恢复重建 | `StockService.java:579-608` | 熔断打开后需连续 PING 成功才整值重建；重建须先取得 `stock:init` 互斥标记 |
| 每日开单对账 | `job/OpenCountReconcileJob.java` | 按"袋当前所处状态"而非订单状态统计，纠正在持数漂移 |

**答辩价值**：本科阶段把"失败路径"写全的不多，多数只讲成功路径。这一节能体现工程成熟度。

### 3.4 JWT 抗算法混淆做得比多数毕设彻底

- `JwtService.java:286-314` **先解 JOSE 头部固定 `alg=HS256`，再验签**，拒绝 RS256→HS256 之类的算法混淆攻击。
- `:119-130` 密钥不足 32 字节（RFC 7518 §3.2 下限）**启动即失败**，不会带弱密钥上线。
- `:273-278` 双密钥轮换窗口按每次验签实时判定，到期后旧密钥自动失效（fail-closed）。

### 3.5 会话吊销分为两级，且缓存删除挂在事务提交后

- jti 黑名单 TTL 取令牌剩余有效期（`AuthService.java:561-576`），登出即失效且无需定时清理。
- `token_version` 实现"禁用/改密/重置/调岗即全量吊销"（`AuthInterceptor.java:236-244`）。
- 版本自增后的 Redis 缓存删除挂在**事务提交后**（`UserService.java:405-435`），避免"提交前删缓存、提交前被并发请求回填旧值"。

### 3.6 脱敏与审计是真做了，不是写在文档里

- `aspect/AuditAspect.java:278-292`：字段名精确命中 `password/phone/recipientPhone`，或名字含 `password`/`phone` 片段即整体脱敏——覆盖命名变体。
- `AuditLogService.java:161-199、270-286`：队列饱和时**关键事件同步落库**、普通事件写应急文件并累加计数，**应用启动时回放**应急文件。
- `common/GlobalExceptionHandler.java:237-242`：系统异常只回 `5000`，全量堆栈仅记日志，不向前端暴露。
- `common/HealthController.java`：`/api/health` 只回 `{"status":"UP"}`，不泄露数据库/Redis/版本等指纹。

### 3.7 降级矩阵是有取舍的，不是敷衍

| 能力 | Redis 不可用时 | 依据 | 评价 |
| --- | --- | --- | --- |
| 设备级 jti 黑名单 | fail-open，窗口 ≤ access-ttl | `AuthInterceptor.java:193-212` | 明确写出"放弃了什么" |
| 账号级失效 | fail-closed，直读 DB | `:221-246` | DB 为权威 |
| 验证码 | fail-closed，拒绝 | `CaptchaService.java:101-115` | 安全凭据不降级 |
| 登录限流 | 放行并记 WARN，由 Nginx 三桶兜底 | `AuthService.java:212-220` | 有兜底路径 |
| 库存申领 | 熔断 → DB 行级降级路径 | `BorrowService.java:364-416` | 用 `FOR UPDATE` 串行化 |

**答辩价值**：能回答"Redis 挂了怎么办"，且答案不是"重启 Redis"。

### 3.8 注入防护与查询安全实际做到位

- 全项目 12 处 `@Select` 全部使用 `#{}` 预编译绑定，**无一处 `${}` 字符串拼接**。
- 三处 `.last("FOR UPDATE")` 是常量，不接受外部输入。
- 排序字段一律走白名单：`UserService.java:549-581` 只接受 `id/createdAt/lastLoginAt`，非法字段直接抛 3001。
- 袋码采用模 31 校验位（`common/util/BagCodeUtils.java:108-117`），格式与校验位在入库前拦截，减少无效查库。

## 四、P0 阻断项（答辩前必须修复）

### P0-1 扫码申领成功后，结果卡永远不会出现

| 项 | 内容 |
| --- | --- |
| 复核状态 | **已复核**（主评审逐行确认） |
| 位置 | `frontend/src/views/user/ScanBorrow.vue:204`、`:365` |
| 影响 | 答辩最可能演示的第一条链路断在半路 |

**现象与证据**

`confirmBorrow()` 在第 204 行成功后只执行 `borrowResult.value = await borrow(...)`，**从未把 `stage` 置为 `'result'`**。全文件对 `stage.value` 的赋值只有四处：

- `:160` → `'loading'`
- `:164` → `'confirm'`
- `:168` → `'query-error'`
- `:236` → `'scan'`（重置）

而结果卡模板在 `:365` 用 `v-if="stage === 'result'"` 渲染。

**实际表现**：用户点完"确认申领"，页面仍停留在确认卡，看不到订单号、看不到"去填写寄件信息"入口；再点一次同一只袋，会因袋已被领取而报错。演示现场会非常尴尬。

**修法**

在 `confirmBorrow()` 的 `try` 与 `catch` 两个分支末尾都补：

```js
stage.value = 'result'
```

`retryBorrow()`（`:216-228`）同理。建议补一条前端用例或至少补一张"成功态"截图入档。

### P0-2 站点实物出库前后端契约不一致，提交必然 3001

| 项 | 内容 |
| --- | --- |
| 复核状态 | **已复核** |
| 位置 | `frontend/src/views/station/StockInOut.vue:85-88`；`backend/src/main/java/com/sems/module/bag/dto/StockOutDto.java:26-27`；`frontend/src/api/bag.js:50-52` |
| 影响 | 任务书④要求的"站点管理员出入库界面"，出库功能当前不可用 |

**现象与证据**

前端提交：

```js
const data = await stockOut({
  bagCodes: stockOutList.value.map((item) => item.bagCode),
  remark,
})
```

后端 DTO 只接受：

```java
@Valid
@NotEmpty(message = "袋码清单不能为空")
private List<Item> bags;   // Item: { bagCode, reason, refCheckNo }
```

`api/bag.js:50-52` 的 `stockOut` 直接透传，没有任何字段映射。因此每次出库都会被 Bean Validation 以"袋码清单不能为空"拒绝，返回 3001。

**更麻烦的第二层**：即便只改字段名，非报废袋仍会被服务层拒绝。`BagService.java:585-589` 规定：

```java
boolean scrapped = status == BagStatus.SCRAPPED;
if (!scrapped && (item.getRefCheckNo() == null || item.getRefCheckNo().isBlank())) {
    throw new BizException(ORDER_STATE_NOT_ALLOWED, "非报废袋出库须填写经批准的盘点差异单号");
}
```

而前端页面只有一个统一的"出库备注"输入框（`:163-171`），没有逐袋的 `refCheckNo`。

**修法**

1. 前端改为逐袋构造：`bags: codes.map(c => ({ bagCode: c, reason: remark }))`；
2. 非报废袋必须逐袋提供盘点差异单号——建议在出库清单行内增加 `refCheckNo` 输入列，或在提交前按袋状态分组，报废袋走一组、差异袋走另一组；
3. 修完后用一只报废袋 + 一只盘点差异袋各跑一次，确认返回逐袋明细。

> 注：如果决定简化为"仅报废袋可出库"，那也必须在 UI 上明确禁掉非报废袋的加入，并同步修改《需求规格说明书》FR-M4-10 的验收口径。当前状态是"文档说两种都支持、前端按一种发、后端按另一种收"，三方不一致。

| 复核状态 | **已复核**（全项目 grep `address` 无命中） |
| 位置 | `backend/src/main/resources/application.yml:3-8`、`application-prod.yml`；`deploy/nginx/nginx.conf.example:39-42`；《系统设计说明书》1245 行 |
| 影响 | 绕过 Nginx 直连后端，整套网络边界设计单点失效 |

**现象与证据**

- `application.yml` 只有 `server.port: 8080`，`application-dev.yml` 只有 `server.port: ${SEMS_DEV_PORT:8090}`，两份 prod/dev 配置**均无 `server.address`**。
- 而 `nginx.conf.example:38-42` 的 upstream 写死 `server 127.0.0.1:8080;`；《系统设计说明书》第 1245 行称"Spring Boot jar（systemd 托管，127.0.0.1:8080）"。

**影响分析**

Spring Boot 的 `server.address` 缺省为 `0.0.0.0`，即监听全部网卡。按当前文档上线，若云服务器安全组未额外收紧 8080，攻击者可直接访问 `http://<公网IP>:8080`，从而：

- 绕过 TLS（JWT 明文传输）
- 绕过 Nginx 注入的 HSTS / CSP / X-Frame-Options 等 5 项安全响应头
- 绕过 Nginx 三桶限流（login/borrow/scan）
- 绕过 Nginx 对 `X-Forwarded-For` 的可信写入

对网络空间安全专业而言，这是最不该漏的一条：**文档写了、配置没写，属于"设计正确、落地缺失"**。

**修法**

在 `application-prod.yml` 增加：

```yaml
server:
  address: 127.0.0.1
```

本地开发若需要手机扫码联调，可在 `application-dev.yml` 单独放开 `0.0.0.0`，与生产隔离。

### P1-3 幂等占位冲突被当成 Redis 故障吞掉

| 项 | 内容 |
| --- | --- |
| 复核状态 | **已复核**（静态）；**待实测**（并发复现） |
| 位置 | `infra/IdempotentService.java:109-111`；`module/order/service/BorrowService.java:680-686` |
| 影响 | 同 `clientRequestId` 并发时可能留下孤儿预扣凭据 |

**证据**

`IdempotentService.markProcessing()` 在 SETNX 未取得时**故意**抛出可重试错误：

```java
if (!Boolean.TRUE.equals(acquired)) {
    throw new BizException(ErrorCode.STOCK_RECONCILING, "相同幂等请求正在处理，请稍后重试");
}
```

但 `BorrowService.markProcessingQuietly()` 用宽泛的 `catch (RuntimeException)` 把它一并吞掉：

```java
try {
    idempotentService.markProcessing(api, crid);
} catch (RuntimeException e) {
    log.warn("幂等占位写入失败（Redis 异常），跳过：...");
}
```

**推演**：同一 `clientRequestId` 的两个并发请求都会继续往下执行，各自生成新 `orderNo` 并各调一次 `tryDeduct`（`:259`）。DB 层由 `uk_order_client_request_id` 只放行一笔；第二笔若命中逐袋幂等回放（`:282-287`），其 Lua 预扣（库存 −1、凭据写入、在持 +1、日频次 +1）**不会走 R0 补偿**——R0 只在 `fire()` 抛异常时触发（`:274-277`）。结果是孤儿凭据 + 库存少计，需等 25h 凭据 TTL 与对账才收敛。

**修法**：把 `catch (RuntimeException)` 收窄为 `catch (DataAccessException)`，让 `BizException(5103)` 正常向上抛出。这样"Redis 故障降级放行"与"幂等冲突拒绝"两种语义才不会被混为一谈。

> 同类问题也见于 `markCompletedQuietly` / `clearQuietly`，建议一并审视：哪些异常代表"基础设施不可用可降级"，哪些代表"业务语义应当拒绝"。

## 七、复核后主动撤回的疑点（避免误改）

以下三条在初评阶段曾被列为疑似缺陷，经主评审回源码核实后**不成立**，特此记录，避免后续"照着改反而改坏"。

### 7.1 盘点单前端多传 `expectJson` / `diffBags` / `diffCount` —— 不是缺陷

`InventoryCheck.vue:181-187` 提交了 `expectJson`、`diffBags`、`diffCount`，而后端 `CreateInventoryCheckDto` 只接收 `actualJson`、`remark`、`stationId`。

**但这是刻意设计**：`InventoryCheckService.java:173` 明确注释——

> 账面数实时统计（3.4.4 处理要点：DB 为权威口径；前端提交的 expectJson 不采信）

后端 `:174-185` 用 `countByStatus(stationId)` 现算账面数，并据此生成差异清单。**客户端无法通过伪造账面数来掩盖盘亏**，这是安全设计而非契约遗漏。

**建议**：前端可以不传这三个字段（减少误导），但后端行为正确，无需改动。

### 7.2 回收确认的批量信封解析 —— 不是缺陷

`RecycleConfirmVo` 继承 `BatchResult`，序列化后确实包含 `data.items / total / success / failed`，与 `utils/batch.js` 的 `extractBatch` 期望一致，并额外带 `proxy / crossStation / directWithoutMark` 三个审计计数。解析正确。

### 7.3 `AuthService.register` 缺少事务 —— 不成立

曾怀疑"角色数据缺失抛错时，用户已插入但角色未插入，留下无角色账号"。核实 `AuthService.java:146` 标注了 `@Transactional(rollbackFor = Exception.class)`，角色缺失时整体回滚，账号不会残留。

## 八、答辩问答准备

以下 6 个问题按"最可能被问"排序，建议逐条写成逐字稿并演练。

### Q1 「现场演示一下扫码取袋。」（最高频）

**准备**：先修 P0-1，然后完整走"扫码 → 袋信息卡 → 确认申领 → 结果卡（订单号）→ 去寄件"。

**若尚未修复**：主动说"这里有个已知缺陷，`stage` 在成功后少赋了一次值，我们已定位并计划修复"，比临场反复点击掩饰得分高得多。

### Q2 「任务书要求站点管理员出入库，你的入库在哪？」

**应答要点**：

1. 讲设计变更：新袋建档即空闲入库、消毒合格自动回空闲并写 `stock_record` 流水，入库动作由"平台建档"与"消毒闭环"承担；
2. 出库保留给"报废袋实物出库"与"经批准的盘点差异出库"；
3. 出示"任务书条目 → 实现落点 → 差异说明"对照表（建议现在就做一张放进 PPT 附录）；
4. **不要**回答"入库没必要"——这会被理解为没读懂任务书。

### Q3 「两只手机同时扫同一只袋，怎么保证不超发？」

**三层防线**：

1. Redis Lua 原子扣减：库存、在持数、日频次、预扣凭据在**一个脚本内**完成（`stock_deduct.lua`）；
2. 状态机条件更新：`WHERE bag_code=? AND status='IDLE' AND version=?`，影响行数为 0 即 4103（`BagTransitionService.java:281-292`）；
3. DB 唯一键兜底：`client_request_id`、运单号联合唯一。

**加分补充**：Redis 故障时走 `borrowDegraded` 的 DB 行级降级路径（`FOR UPDATE` 串行化），失败走 R0 同步补偿，残留由 R4 每 30 分钟对账收敛。

### Q4 「条件 UPDATE 里为什么既要 `status` 又要 `version`？只留 `version` 不行吗？」

**应答**：`version` 只保证"这一行没被别人改过"，`status` 保证"这一行的前态符合本次事件的业务语义"。两者都进 WHERE，才能在**同一条 SQL** 里原子判定"未被他人领取 **且** 当前确实空闲"。MyBatis-Plus 的乐观锁插件只能追加 `version` 一个条件，所以这里手写 `UpdateWrapper`。

### Q5 「你审计日志里的 IP，能作为追责证据吗？」（尖锐题）

**诚实应答**：操作审计与全局异常两处取 `X-Forwarded-For` 最右段（由可信 Nginx 追加，不可伪造）；但**登录日志、越权审计、"查看完整 IP"三处仍取最左段，客户端可自带该头伪造**，这是我们已定位、待统一的缺陷，正确口径应统一为最右段。

**为什么这样答**：这一条老师只要看一眼代码就能发现。主动承认 + 说清修复方案，体现的是"知道自己的系统哪里不干净"，这恰恰是安全专业该有的素养；硬撑反而暴露没读过自己的代码。
