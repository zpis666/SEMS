## 一、总体评价

### 1.1 先说做得好的地方

本轮审计与上一轮（2026-10-05，V1.0→V1.1）相比，文档质量有明显台阶，以下判断经核验成立：

1. **上一轮的两大根因已真正根治**。状态机"闭集"问题（根因 A）已解决——3.2 现有 21 条转移，**每条都能在 5.x 接口表中找到触发接口**，无滞留态、无不可达态、无同一 (前态,事件) 的双重映射，库存与计数副作用逐条标注；时限与计数口径（根因 B）已收敛为 3.5 单一权威表，全文时限数字基本收口。
2. **需求侧首次形成完整的编号体系**。FR 111 条（M1 18 / M2 13 / M3 21 / M4 24 / M5 21 / M6 14）编号连续无缺号，与 REQ 4.1、10.2 计数自洽；**DES 引用的 42 个 FR 编号与 17 个 NFR 编号无一悬空**，两份文档的追溯矩阵逐行对得上。
3. **数据库设计与建表脚本的机械一致性极高**。21 张表、217 个字段、81 个索引逐一比对，字段名、类型、可空、默认值、注释、索引列序、字符集全部一致；静态检查（保留字反引号、索引前缀、DATETIME 默认值、建表顺序）无异常——**这一项（DB↔DDL）是全部 14 路中唯一近乎零缺陷的一路**。
4. **并发方案的骨架是完整的**。Lua 原子扣减 + R0–R4 回补 + 降级矩阵 + DB 条件 UPDATE 末道防线，13 个 Redis 键在 DES 8.3 与 DB 第 6 章逐条一致。本轮发现的问题集中在**异常分支的语义闭合**，而非方案本身选错。

### 1.2 本轮的五类系统性根因

77 条问题里绝大多数不是孤立笔误，可归为五类根因。**建议按根因成批修订，而不是逐条打补丁**——上一轮"按根因成批处理"的做法效果很好，本轮沿用：

- **根因 1：多轮增量修订的"接缝"没有回扫。** V1.3→V1.7 连续五轮加内容（视觉规范、命名、版本基线、与数据库对齐、补接口缺口），每轮只改增量处，**没有回扫被增量影响的既有章节**。典型：V1.6 为承载审计丢弃计数新增了 `sys_metric` 表，却没补读取接口（P1-18）；V1.7 新增 `/alerts` 却没把 7.6 承诺的丢弃计数挂进去（P1-18）；V1.6 把设计书对齐到数据库，却没回改需求书 10.3 的版本引用（P2-34）。**修订纪律建议：每次升版必须列出"被本次改动影响、因而必须回扫的章节清单"。**

- **根因 2："承诺了载体，但没有生产者或消费者"。** 上一轮根因 C 提出"状态+单据+接口+页面四件套核对"，本轮显示该纪律**没有制度化**，因而复发：7.6 承诺丢弃计数"在 5.6 看板告警"，但看板无该指标、无接口（P1-18）；9.1 承诺"Nginx + 应用层双重限流"、7.2 承诺降级期"退化为 Nginx 兜底"，但 11.x 与 `deploy/nginx` 无任何 `limit_req` 配置（P1-20）；REQ NFR-MNT-04 要求"运维手册"，但五份交付物里没有它（P1-34）；5.6 写"风控线索由确认类频次阈值触发"，而全文无任何阈值数值（P1-22）。**建议：把"四件套核对"作为每次升版的固定检查表，凡出现"告警/看板/提醒/可据此"字样，一律反查读取方。**

- **根因 3：权威口径表声称"唯一定义于此"，实际未承担该角色。** 3.5 自述"全文时限与计数唯一定义于此，不得另设数值"，但 `borrow:open` 的 TTL 口径（P1-12）、风控阈值（P1-22）、批量上限（P1-9）均未登记；6.4 是错误码权威表，但**错误码 → HTTP 状态的映射全文没有唯一出处**，6.6 两行自相矛盾（P1-11）；调拨单状态枚举在 DES 8.2 与 DB 4.2 各说一套（P1-19）。**建议：把 3.5/6.4 扩为"口径登记册"，凡正文出现数值或枚举，一律回登记册取号。**

- **根因 4：降级与异常路径只写到"意图层"，没写到"实现层"。** 这是本轮**新增的、也是危害最大的一类**：jti 黑名单"fail-closed 不静默放行"（P0-3）、初始化期返回 5102（P1-15）、幂等"处理中"占位（P1-21）、R0 补偿的原子性与幂等方向（P1-13）。这些句子在意图上都对，但**缺少可编码的判定条件、存储结构与时序**，而异常分支恰是 NFR-REL-02/03 的验收考核点——按字面实现会得到"Redis 一挂全站拒绝服务"这种与设计目标相反的结果。

- **根因 5："跨站 / 跨态 / 迟发"这类组合维度未系统化。** 单个维度（本站、正序、按时）的流程都写得很清楚，但组合起来就出现空洞：#4 未使用回收跨站时归属改不改（P1-23）、#21 跨站同态修正两站库存动不动（P0-4）、调拨锁定挡不挡报废/维修（P1-28）、24h 取消后才寄出的袋怎么回流（P1-29）。**建议：为状态机补一张"跨站 × 跨态"的副作用矩阵，把这些组合一次性穷举。**

### 1.3 结论

**本轮审计不通过合规闸门。** 5 条 P0 会在编码第一周就变成返工；36 条 P1 会让接口测试用例无法统一断言。但需要强调的是：**这不是文档推倒重来，而是收口**——架构、技术选型、状态机骨架、并发方案、数据库结构五项立柱均无损，问题集中在语义闭合与口径对齐，可在一次集中修订中解决。

## 二、必须修改（P0：编码动手前必须定稿）

### P0-1 遗失确认后订单终态二义：被取消的订单是"保持已取消"还是"转已遗失"

- **位置**：REQ L1637（UC-P04 主流程 6）、L1627（后置条件）、L954/957（FR-M5-14）；DES L328（3.2 转移表 #18）
- **问题**：UC-P04 主流程 6 写"口径③ 订单已取消 → **订单保持已取消**，不重复扣减计数"；同一用例的后置条件与 FR-M5-14 的描述/验收却写"**订单与袋均转已遗失**"；设计书 #18 的伴随动作也是"订单→已遗失"。
- **后果**：被取消订单在确认遗失后有两个合法终态。订单表数据、用户端"我的订单"展示、看板统计口径三者不一致；**接口测试按任一条款写断言都会撞另一条**，且订单交付物（测试报告）无法给出确定结论。这属于典型的"需求自相矛盾"，测试报告无法通过评审。
- **修改建议（采纳"转已遗失"，三处同步）**：以 `bag.status` 为权威事实（REQ 7.4 DC-01），袋既然转为已遗失，订单必须跟随，否则违反 DC-01 的联动要求；且责任认定记录（`liability_record`）以"该订单已遗失"为前提。故：
  1. UC-P04 主流程 6 改为"口径③ 订单已取消 → 订单**由已取消转已遗失**（终态覆盖），**不重复扣减**未归还订单计数（该计数已在撤回/超时时递减）"；
  2. UC-P04 后置条件统一为"三种口径下：袋→已遗失，订单→已遗失"；
  3. FR-M5-14 描述与验收口径保持"订单与袋均转已遗失"，并补一句"已取消订单被确认遗失时不重复扣减未归还订单计数"。

### P0-2 站点停用前置条件自相矛盾：同一节内表行与表后说明给出两套校验

- **位置**：DES L570（5.3 接口表行）、L584（同节表后说明）、L894（8.2 表概要）；REQ L563-568（FR-M3-04）、L292（BR-14）
- **问题**：5.3 表格行写"停用前置：**可用库存为 0**，需先调拨移交"；同节的表后说明却写"停用前置须将**非终态实物清零**……仅『可用库存为 0』不足以停用"；8.2 又重复了宽松口径。REQ 侧 FR-M3-04 与 BR-14 均为**双条件**。
- **后果**：停用校验是本项目数据一致性的一个真实检查点（可用库存只统计空闲袋，待消毒/可复用/未激活三类袋不进入该口径）。若实现者照表行（或照 8.2）编码，含待消毒袋的站点会被放行停用，这些袋随之"失联"；而按 REQ 验收又判不符。**同一节里两种口径，实现者只能二选一，选错即验收失败。**
- **修改建议（统一为双条件，三处同步）**：
  1. DES L570 表格行改为"停用前置：**可用库存为 0 且非终态实物已清零或已指定接收站**（见本节表后说明）"；
  2. DES L894（8.2 表概要）同步为同一句；
  3. 与 P1-33（"指定接收站"无数据载体）**一并落地**：`station` 表增 `handover_station_id` 字段、`PUT /stations/{id}` 增参数字段并校验写入，否则"已指定接收站"这一半条件同样无法实现。

### P0-3 jti 黑名单的降级策略不可实现，且与降级期可用性目标互斥

- **位置**：DES L804（7.2 降级矩阵行）、L795（同节降级目标）、L715（7.1 黑名单）、L925（8.3 键空间）；REQ L1728（NFR-REL-03）
- **问题**：7.2 降级矩阵写"jti 黑名单：**fail-closed：降级期拒绝该用户 token（或查 DB 兜底）**，不因 Redis 不可用而放行"；但同一节的降级目标是"熔断后**申领直走 DB 行级路径**……**仅损失吞吐**"。而 jti 黑名单只存在于 Redis（8.3），"查 DB 兜底"**没有对应的表**。
- **后果**：按字面实现，Redis 故障期**任何带 token 的请求都无法核验黑名单**，于是要么全部拒绝（与"申领走 DB 路径、仅损失吞吐"直接冲突，也与 NFR-REL-03"断 Redis 压测下申领仍无超发"的验收场景互斥——那个场景要求降级期业务继续可用），要么全部放行（与"不因 Redis 不可用而放行"冲突）。**两条路都与文档的另一半矛盾，实现者无解。**
- **修改建议（按"账号级 vs 设备级"分层，采纳 fail-open + 分层兜底）**：把两类失效语义分开，这是本问题的关键——它们的安全性要求本就不同：
  1. **账号级失效必须保持即时**（禁用、改密、重置、改角色、换绑站点）：`sys_user.token_version` 是权威值且**在数据库里有表**，Redis 只是 60 秒读加速。降级期改为**直读 DB 比对 token_version**，安全性不降（这正是"封号即失效"的主保障）。
  2. **设备级失效降级期接受窗口**（单设备登出）：jti 黑名单仅存 Redis、无 DB 兜底表。降级期改为 **fail-open 放行**，失效窗口 = 该 token 的剩余有效期（access token ≤2 小时），并把"降级期全部请求记 WARN 审计"作为补偿性控制。
  3. 7.2 该行改写为："jti 黑名单（单设备登出）：降级期 **fail-open**，账号级失效由 token_version 直读 DB 保证；窗口 ≤ access token 剩余有效期（≤2h），降级期请求记 WARN 审计，恢复后黑名单继续生效。**删除"查 DB 兜底"表述**。"
  4. 在 9.1 威胁分析补一行"风险接受：Redis 故障期单设备登出失效窗口 ≤2h"，避免答辩时被问而无据。

### P0-4 #21 状态修正的库存口径在跨站时漏账（跨站同态修正两站都不动）

- **位置**：DES L331（3.2 转移表 #21 伴随动作）；REQ L1474（UC-S07 备选流 7b）、L1664（UC-P05 主流程 6）、L787 附近（FR-M4-16 验收）
- **问题**：#21 的库存规则是"源=空闲且目标≠空闲 → Redis −1；目标=空闲 → Redis +1；**源=目标时不动**"。当盘点发现"本站在册的空闲袋实物其实在另一站"时，修正为**跨站同态**（空闲→空闲，`station_id` 由 A 改 B）：按"源=目标时不动"，**A、B 两站库存都不变**——但实物已经从 A 挪到 B，A 的可用库存虚高 1、B 缺 1。而 REQ UC-S07 备选流 7b 明确要求"修正涉及跨站归属 → 同步 `station_id`，**两站库存分别增减并推送**"。两套文档对同一操作给出相反指令。
- **后果**：跨站同态修正是盘点的常见情形（异地投箱、错站归还都会产生）。按 #21 实现，**两站账实背离**，直至下一轮 R4 对账（≤30 分钟）才纠正；期间 B 站可能因库存虚低拒绝申领、A 站可能因虚高而超发。验收方面，UC-S07 的断言（两站分别增减）必然失败。
- **修改建议（跨站优先于同态，四条同步）**：把 #21 的库存规则从"看状态是否相同"改为"**看库存归属站点是否变更**"：
  1. #21 伴随动作改为："按**源/目标站**计算：源站计可用库存（源态=空闲）且（跨站 或 目标态≠空闲）→ 源站 −1；目标站计可用库存（目标态=空闲）且（跨站 或 源态≠空闲）→ 目标站 +1；**仅当同站且同态时不动**。跨站一律同步 `station_id` 并推送两站库存变更。"
  2. UC-P05 主流程 6 同步为同一句；
  3. FR-M4-16 验收口径补"跨站修正须验证两站库存分别增减且 `station_id` 已同步"；
  4. UC-S07 备选流 7b 保持（它本来就是对的），并在 DES 3.2 表后说明补一句"#21 的库存规则以『库存归属站点是否变更』为准，不受状态是否相同影响"。

### P0-5 超期归档清理：清理对象写错表，且清理这件事在系统设计里不存在

- **位置**：DB L767（5.4 备份与归档）、L825（7.3 审计留痕）、L748-761（5.3 容量估算）；REQ L1769-1776（7.2 数据保留期）；DES L857（7.6 防篡改三层）、L839-853（7.5 定时任务）
- **问题**：这是**三处叠加**的问题，必须一起改：
  1. **清理对象写错**：DB 5.4 写"`bag_transfer_log`、`audit_log` 超过保留期后归档导出并清理"，而同一份文档 7.3 把 `bag_transfer_log` 的保留期标为"**长期**"，REQ 7.2 也写"快递袋流转日志 | 长期保留"。照 5.4 执行，会定期删除须长期保留的流转日志——**而这正是责任认定与 NFR-REL-05 回溯链的唯一载体**。
  2. **该清的没清**：保留期同为 ≥180 天的 `login_log` 反而未列入清理范围。
  3. **清理本身没有实现落点**：REQ L1776 要求"超过保留期的审计数据归档导出后清理，**清理操作本身也必须写审计日志**"，但 DES 7.5 的定时任务清单里**没有清理任务**，全文检索无"归档/清理"；而 7.6 又规定应用数据库账号对 `audit_log`/`login_log` **仅授 INSERT、SELECT**——即便写了任务也没有 DELETE 权限。
- **后果**：不实现则审计数据无限增长、REQ 7.2 的 180 天合规无法验证、NFR-MNT-03 无法验收；照 DB 5.4 字面实现则**删掉不可再生的事故追溯证据**（比不实现更糟）。这是本轮唯一一条"照文档做会造成不可逆数据损失"的问题。

  1. DB 5.4 归档范围改为"**`audit_log`、`login_log`** 超过保留期（≥180 天 + 缓冲）后归档导出并清理"；`bag_transfer_log` 明确"**长期在线保留，不参与清理**"；同步删除 5.3 容量估算中"按 `created_at` 归档清理"的表述。
