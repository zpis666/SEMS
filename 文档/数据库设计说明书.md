## 2 设计概述

### 2.1 设计目标与原则

| 编号 | 原则                     | 具体落实                                                                 |
| ---- | ------------------------ | ------------------------------------------------------------------------ |
| D1   | 以袋状态为权威事实       | 袋状态由状态机统一驱动，订单状态跟随联动，避免双状态各自演化产生不一致   |
| D2   | 全程可追溯               | 每一次状态流转写 `bag_transfer_log`；高风险操作写 `audit_log`；流水类表只插入不更新 |
| D3   | 并发安全                 | 库存并发由 Redis 原子扣减保证，数据库侧以 `version` 乐观锁 + 条件更新作为最后防线；唯一键兜底防重 |
| D4   | 敏感数据最小化           | 收件人手机号不落明文；用户手机号出参脱敏；口令只存 BCrypt 摘要            |
| D5   | 账实一致                 | 库存计数与实物状态严格对应；对账、盘点、调拨均以实物为锚                 |
| D6   | 单库单机、够用即可       | 不分区、不分表、不引入分布式组件；以索引设计保证校园规模下的查询性能     |
| D7   | 结构可演进               | 枚举用字符串而非 `ENUM`，新增状态或类型无需改表结构                      |

### 2.2 命名规范

| 对象         | 规范                                                                 | 示例                                     |
| ------------ | -------------------------------------------------------------------- | ---------------------------------------- |
| 表名         | 小写字母 + 下划线，名词单数，业务表不加前缀；系统级表以 `sys_` 开头    | `bag`、`bag_order`、`sys_user`           |
| 字段名       | 小写字母 + 下划线；布尔语义用 `is_xxx` 或直接语义化命名               | `bag_code`、`timeout_flag`、`created_at` |
| 主键         | 统一名为 `id`                                                         | `id`                                     |
| 外键列       | `<关联实体>_id`；关联到业务编码时用 `<编码名>`                        | `station_id`、`bag_code`                 |
| 主键约束     | `PRIMARY`                                                             | —                                        |
| 唯一索引     | `uk_<表名简写>_<字段>`                                                | `uk_bag_code`                            |
| 普通索引     | `idx_<表名简写>_<字段>`                                               | `idx_bag_station_status`                 |
| 外键索引     | `fk_<表名简写>_<字段>`                                                | `fk_order_station_id`                    |
| 时间字段     | 创建 `created_at`、更新 `updated_at`；业务时间按语义命名             | `dispatch_at`、`scrap_time`              |

### 2.3 通用字段约定

| 约定                     | 规则                                                                                         |
| ------------------------ | -------------------------------------------------------------------------------------------- |
| 主键                     | `id bigint unsigned NOT NULL AUTO_INCREMENT`，全库统一，不使用 UUID 或雪花 ID（单机单库无冲突压力） |
| 创建时间                 | `created_at datetime(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)`，所有业务表必备               |
| 更新时间                 | `updated_at datetime(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3)`，仅在有更新语义的表上设置 |
| 业务单号                 | 对外单号（`order_no`、`allocation_no`、`batch_no`）单独建唯一索引，不与主键混用               |
| 操作人                   | 统一为 `operator_id bigint unsigned`，指向 `sys_user.id`；平台管理员代操作时记平台管理员      |
| 逻辑删除                 | **本系统不使用逻辑删除**：档案类实体的"停用"通过 `status` 表达，流水与日志类数据只插入不删除；误建且无业务引用的记录走物理删除并写审计日志 |

> **关于逻辑删除的取舍**：初稿曾计划对 `station`、`bag`、`sys_user` 引入 `deleted` 标志位。但逻辑删除会与业务唯一键（站点名、袋码、手机号）冲突——软删后该值被永久占用，无法重建同名站点或同码袋。本系统的档案实体本就有 `status` 字段承担"停用/报废"语义，无需再引入一层逻辑删除，故统一取消。

### 2.4 数据类型选用约定

| 场景           | 选用                                        | 理由与禁止项                                                                 |
| -------------- | ------------------------------------------- | ---------------------------------------------------------------------------- |
| 时间           | `datetime(3)`（毫秒精度）                    | **禁止使用 `timestamp`**：受 2038 年上限与时区转换影响；全库时区固定 `+08:00` |
| 布尔语义       | `tinyint unsigned`（0/1）                    | 不用 `bit`、不用 `boolean`（MySQL 中实为 `tinyint(1)`，语义易混）             |
| 枚举语义       | `varchar(20)` + 中文注释                     | **禁止使用 `ENUM`**：新增状态需 `ALTER TABLE`，与"结构可演进"原则冲突         |
| 计数           | `int unsigned`（大计数用 `bigint unsigned`） | 避免负数，天然约束不合法输入                                                 |
| 金额           | 本系统不涉及资金流转，不设金额字段           | 若未来引入押金，按 `decimal(10,2)` 处理                                       |
| 短文本         | `varchar(n)`，按实际长度上限设定             | 禁止一律 `varchar(255)`；长度本身是一道校验                                  |
| 长文本 / 结构化 | `text` / `json`                              | 仅在确有必要时使用（如盘点的差异清单、统计快照）                             |
| 编码类         | `varchar(20)`，跨表必须一致                  | 如 `bag_code` 在 8 张表中长度必须相同，否则索引与比较失效（见 4.4）            |
| IP 地址        | `varchar(45)`                                | 兼容 IPv6                                                                     |

### 2.5 数据库环境与参数

| 项         | 取值                                                         |
| ---------- | ------------------------------------------------------------ |
| 版本       | MySQL 8.0                                                    |
| 存储引擎   | InnoDB（全部表）                                             |
| 字符集     | `utf8mb4`                                                    |
| 排序规则   | `utf8mb4_0900_ai_ci`（大小写不敏感，与业务唯一性判断一致）     |
| 时区       | `+08:00`（服务端与连接均固定，不依赖操作系统时区）             |
| 事务隔离级别 | `REPEATABLE READ`（MySQL 默认）                            |
| 表名大小写 | `lower_case_table_names = 0`（Linux 默认，全小写表名不受影响） |
| 连接池     | HikariCP，`maximum-pool-size=20`（见《系统设计说明书》11.1）  |

## 3 概念设计

### 3.1 实体清单

全部实体按业务域分为六组，共 **21 张表**：

| 业务域       | 表                                  | 说明                                             |
| ------------ | ----------------------------------- | ------------------------------------------------ |
| 用户与权限   | `sys_user`、`sys_role`、`sys_user_role` | 三类角色共用一张用户表，角色经关联表多对多           |
| 站点与库存   | `station`、`stock_record`            | 站点档案与出入库流水                             |
| 快递袋       | `bag`、`bag_transfer_log`            | 袋档案（含当前状态与归属）与状态流转日志           |
| 订单与责任   | `bag_order`、`liability_record`、`stock_compensation_log` | 快递订单、责任认定记录、库存补偿日志 |
| 作业单据     | `disinfect_record`、`disinfect_detail`、`repair_record`、`scrap_record`、`inventory_check`、`allocation_order`、`allocation_detail` | 消毒/维修/报废/盘点/调拨的单据 |
| 审计与统计   | `audit_log`、`login_log`、`stats_daily`、`sys_metric` | 操作审计、登录审计、日统计与系统指标 |

### 3.3 关系说明

| 关系                                       | 基数 | 说明                                                                 |
| ------------------------------------------ | ---- | -------------------------------------------------------------------- |
| 站点 — 快递袋                               | 1:N  | `bag.station_id` 表示**当前存放站点**，随回收确认、调拨入库等实物转移事件变更 |
| 快递袋 — 流转日志                           | 1:N  | 每次状态流转写一条，1 只袋全程产生多条，是追溯的核心依据               |
| 用户 — 订单                                 | 1:N  | 一个用户可发起多个订单；同一时刻未完结订单受"未归还 ≤3"约束           |
| 订单 — 快递袋                               | N:1  | 一个订单绑定一只袋；同一只袋同一时刻只能绑定一个未完结订单             |
| 用户 — 站点                                 | N:1  | `sys_user.station_id` 实现站点管理员的单站绑定（一岗一站）             |
| 站点 — 消毒批次 — 明细                       | 1:N:M | 一次消毒作业覆盖多只袋，明细逐袋记结果                               |
| 调拨单 — 明细 — 快递袋                       | 1:N:M | 调拨单建单即锁定明细中的袋，核收后变更归属                            |
| 订单 / 调拨单 — 责任记录                     | 1:N  | 遗失、在途遗失、超时等异常均可生成责任认定记录                        |

### 4.2 表结构详细设计

> 下列各表中，"键"列的取值为：`PK` 主键、`UK` 唯一键、`FK` 逻辑外键（只建索引，不建物理约束）、`IDX` 普通索引列。
> "允许空"为"否"的列在 DDL 中为 `NOT NULL`；"默认值"为"自增"的列在 DDL 中为 `AUTO_INCREMENT`。

#### 4.2.1 `sys_user` — 用户账号表（三角色共用）

| 字段 | 类型 | 允许空 | 默认值 | 键 | 说明 |
| --- | --- | --- | --- | --- | --- |
| `id` | bigint unsigned | 否 | 自增 | PK | 用户ID（自增主键） |
| `phone` | varchar(11) | 否 | — | UK | 登录手机号，出参脱敏 |
| `password` | varchar(60) | 否 | — | — | 密码BCrypt摘要（cost≥10） |
| `nickname` | varchar(32) | 否 | — | — | 昵称（注册必填） |
| `status` | varchar(20) | 否 | 'ENABLED' | — | 账号状态：ENABLED启用/DISABLED禁用 |
| `station_id` | bigint unsigned | 是 | — | FK | 绑定站点ID，仅站点管理员非空 |
| `token_version` | int unsigned | 否 | 0 | — | 令牌版本，自增即全量吊销 |
| `must_change_password` | tinyint unsigned | 否 | 0 | — | 须强制改密（预置/重置账号） |
| `last_login_at` | datetime(3) | 是 | — | — | 最后登录时间 |
| `last_login_ip` | varchar(45) | 是 | — | — | 最后登录IP（兼容IPv6） |
| `created_at` | datetime(3) | 否 | CURRENT_TIMESTAMP(3) | — | 创建时间（注册时间） |
| `updated_at` | datetime(3) | 否 | CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3) | — | 更新时间，随修改自动刷新 |

#### 4.2.3 `sys_user_role` — 用户与角色关联表

| 字段 | 类型 | 允许空 | 默认值 | 键 | 说明 |
| --- | --- | --- | --- | --- | --- |

### 4.3 外键与完整性约束策略

**统一采用逻辑外键**：所有关联关系只建索引、不建物理 `FOREIGN KEY` 约束。理由如下：

1. **性能**：物理外键在每次写入时都要回查父表并可能加锁，对高频写入的流水表（`bag_transfer_log`、`stock_record`、`audit_log`）是不必要的开销。
2. **可控性**：删除/停用的前置校验（如站点停用前须实物清零）逻辑复杂，放在服务层比交给数据库约束更清晰，错误提示也更友好。
3. **可维护性**：分阶段建表与数据初始化不受外键顺序限制，便于部署与回滚。

索引命名以 `fk_` 开头即表示"这是一个逻辑外键的索引"，便于识别。

**完整性由三层保证**：

| 层次       | 手段                                                                 | 覆盖的问题                                     |
| ---------- | -------------------------------------------------------------------- | ---------------------------------------------- |
| 数据库层   | 主键、唯一索引、`NOT NULL`、字段长度                                 | 重复、缺失、超长                               |
| 服务层     | 状态机校验、数据权限校验、停用前置校验                               | 非法状态跳变、越权、业务前置条件不满足         |
| 应用并发层 | `version` 乐观锁 + 条件更新、Redis 原子扣减、幂等键                  | 重复领取、超发漏发、重复提交                   |

### 4.4 索引设计原则

| 原则               | 说明                                                                                 |
| ------------------ | ------------------------------------------------------------------------------------ |
| 每一个索引都有用途 | 索引注释必须写明它服务哪个查询场景；无明确查询场景的索引不建                         |
| 编码类字段长度一致 | `bag_code` 在 8 张表中统一为 `varchar(20)`，长度不一致会导致跨表比较与索引失效        |
| 唯一键优先         | 能用唯一索引约束的业务规则（袋码、单号、幂等键）一律用唯一索引兜底，不只依赖应用判断 |
| 覆盖高频组合查询   | 如 `(station_id, status)` 直接服务"站点可用库存统计"这一最热查询                     |
| 避免冗余           | 已有 `(station_id, status)` 时不再单建 `(station_id)`，两者左前缀重复                |
| 时间列常作次列     | 流水与日志类表普遍采用"实体列 + `created_at`"的组合索引，兼顾筛选与排序              |

### 5.3 容量估算

按校园规模假设（站点 ≤ 50 个、快递袋 ≤ 10000 只、日均订单 ≤ 2000 单）估算一年数据量：

| 表                            | 年增行数（估） | 说明                                       |
| ----------------------------- | -------------- | ------------------------------------------ |
| `bag_order`                   | ~70 万         | 日均 2000 单，一年                           |

## 6 Redis 键空间设计

Redis 只承担三类职责：**库存计数**、**过期控制**、**读加速**。它不是权威存储，所有键都可以从 MySQL 重建，这是"Redis 故障不导致数据错误"的前提。

| Key 模式 | 类型 | TTL | 用途 |
| --- | --- | --- | --- |
| `stock:available:{stationId}` | String | 无（对账维护） | 站点可用库存计数，权威在 DB，本键为读写视图 |
| `stock:hold:{orderNo}` | String(json) | 25 小时 | 预扣凭据（仅凭据，取消语义在订单表） |
| `stock:init:{stationId}` | String(标记) | 300 秒 | 库存计数初始化互斥标记 |
| `stock:reconcile:{stationId}` | String(标记) | 120 秒 | 库存对账互斥标记 |
| `borrow:open:{uid}` | String(int) | 14 天滑动 | 未归还订单计数（≤3，进入三态 +1、离开三态 −1） |
| `borrow:daily:{uid}:{yyyyMMdd}` | String(int) | 当日 +1 天 | 取袋日频次（≤10） |
| `auth:deny:{jti}` | String | 等于 token 剩余期 | JWT 黑名单，实现单设备登出 |
| `auth:userver:{uid}` | String | 60 秒 | token_version 读缓存（权威在 DB） |
| `login:fail:{phone}` | String | 15 分钟 | 登录失败计数，达 5 次锁定 |
| `captcha:{captchaId}` | String | 3 分钟 | 图形验证码，一次性 |
| `idempotent:{uid}:{api}:{clientRequestId}` | String(json) | 10 分钟 | 写操作幂等去重 |
| `rate:{uid或ip}:{api}` | String(int) | 1 分钟窗口 | 固定窗口限流（登录、取袋、扫码查询） |
| `stats:today:{stationId}` | Hash | 当日 24 时 +4 小时 | 今日取/还实时计数，看板读取 |

> **重建顺序**（Redis 数据丢失或故障恢复后）：先按站点 `COUNT(bag WHERE status='IDLE')` 重建 `stock:available`，再扫描 `stock:hold:*` 做孤儿凭据检查（见《系统设计说明书》7.2 R3）；计数类键（`borrow:*`）按数据库订单状态重建。**所有键均可重建，Redis 不承担权威存储职责。**

## 7 数据安全设计

### 7.1 敏感字段与脱敏

| 字段                       | 存储方式                                       | 展示方式                         | 说明                                                   |
| -------------------------- | ---------------------------------------------- | -------------------------------- | ------------------------------------------------------ |
| `sys_user.password`        | BCrypt 摘要（cost ≥ 10）                       | 永不返回                         | 单向哈希，不可逆                                       |
| `sys_user.phone`           | 明文（业务必需，用于登录与联系）               | 出参一律掩码 `138****1234`       | 查询与唯一性校验需要原值                               |
| `bag_order.recipient_phone_mask` | 掩码                                    | 直接展示                         | 展示用                                                 |
| `bag_order.recipient_phone_hash` | HMAC-SHA256（带盐）                      | 永不返回                         | **仅用于核对比对（如查同一收件人的历史订单），不可还原** |
| `audit_log.params_masked`  | 已脱敏的请求参数快照                           | 仅平台管理员可见                 | 落库前完成脱敏，禁止落原始参数                          |

> **为什么收件人手机号要"掩码 + 哈希"双列**：业务上需要展示（掩码足够）与核对（哈希足够），两者都不需要还原明文。因此系统**不存储收件人手机号的明文**——这是本系统相对"存明文再脱敏"方案的安全增强点，即使数据库泄露也无法直接还原收件人号码。

### 7.2 最小授权

| 账号         | 权限                                                              |
| ------------ | ----------------------------------------------------------------- |
| 应用账号     | 业务表的 `SELECT / INSERT / UPDATE`；**不授予 `DROP`、`GRANT`**    |
| 审计表专项   | 对 `audit_log`、`login_log`、`stock_compensation_log` **仅授予 `INSERT`、`SELECT`**，从数据库层面保证审计记录不可篡改 |
| 备份账号     | 仅 `SELECT`、`LOCK TABLES`、`RELOAD` 等备份所需权限                |
| 网络访问     | MySQL 仅监听内网，不对公网开放（见《系统设计说明书》11.1）          |

### 7.3 审计留痕

| 表                       | 记录内容                                                     | 保留期  |
| ------------------------ | ------------------------------------------------------------ | ------- |
| `audit_log`              | 全部写操作的操作人、IP、UA、模块、动作、脱敏参数、结果、耗时   | ≥180 天 |
| `login_log`              | 登录成功/失败、失败原因、IP、UA                               | ≥180 天 |
| `bag_transfer_log`       | 每一次袋状态流转的前后状态、事件、操作人、站点                | 长期    |
| `liability_record`       | 责任认定的结论、责任人、决定人与决定时间                       | 长期    |
| `stock_compensation_log` | 库存补偿的触发原因与幂等键，用于事后核查是否重复补偿           | 长期    |

**审计重点核查项**（平台管理员在审计界面应能直接筛出）：报废登记、状态修正、盘点差异修正、遗失认定、责任裁决、回收确认（含跨站与未标记直投）。

`audit_log` 采用异步落库（独立线程池 + 有界队列）。队列饱和时，关键事件降级为同步写，普通事件写入本地应急文件并累加丢弃计数器；**丢弃计数器落库到 `sys_metric` 并在数据看板告警**，确保审计写入高峰（往往正是攻击高峰）既不拖垮业务，也不静默丢失。

## 8 附录

### 8.1 设计校验记录

本文档的表结构经两类对抗校验后定稿，校验发现并已修正的问题如下：

| 类别           | 问题                                                         | 处置                                                     |
| -------------- | ------------------------------------------------------------ | -------------------------------------------------------- |
| 跨表一致性     | `bag_code` 在 8 张表中长度不一致（部分 `varchar(32)`）        | 统一为 `varchar(20)`（袋码定长 18 位，留 2 位余量）        |
| 缺失索引       | 4 个逻辑外键列未建索引（消毒、维修、报废表的操作人列）        | 补齐 `fk_` 索引                                           |
| 缺失表         | 设计书 7.6 要求审计丢弃计数"落库并在看板告警"，但无表承载     | 新增 `sys_metric` 系统指标表                              |
| 缺失字段       | `bag_transfer_log` 无字段承载"状态修正必填的盘点差异单号"     | 新增 `ref_check_no`，使状态修正可按盘点单反查              |
| 缺失字段       | 调拨单"异常终止"缺时间与原因承载                              | 扩充 `cancel_reason` 语义并新增 `abnormal_at`、`terminated_by` |
| 冗余索引       | `bag` 表的单列 `station_id` 索引被 `(station_id, status)` 覆盖 | 删除冗余索引                                             |
| 索引缺口       | `bag.status`、`bag_order.created_at` 等高频筛选列无前导索引   | 补齐                                                      |
| 唯一键与软删   | 逻辑删除会使站点名、袋码被永久占用，无法重建                 | **取消全部逻辑删除**，停用改由 `status` 表达（见 2.3）     |

### 8.2 与《系统设计说明书》第 8 章的差异

本文档相对设计说明书第 8 章的**新增**（设计说明书为概要，字段未展开，此处不构成冲突）：
